# Plan: oxdock-ssh-plugin (user-space ephemeral SSH server bridged to stdio pipes)

## Goal
New crate `crates/plugins/oxdock-ssh-plugin` exposing SSH connectivity through the Engine facade as a compile-time `HostModule SSH`, with v1 use case: spin up an ephemeral user-space SSH server (random or caller-supplied username/password, in-memory host key, loopback bind, no OS users, no sshd_config, no Docker) and route each session through OxDock stdio pipelines (`WITH_IO` + `ASYNC` pipe bridging in the style of `net_bridge.rs`).

## Decisions (from user)
- Runtime: tokio + russh scoped **inside the plugin crate only** (core stays sync `std::thread` + `std::process`).
- Surface: `HostModule` funcs/types via `Engine::register_module`. No new DSL grammar.
- Session behavior v1: bridge channel bytes to stdio pipes. Upstream `ssh user@host` hop is deferred (non-goal for v1).
- Location/name: `crates/plugins/oxdock-ssh-plugin` (new `crates/plugins/` group).

## Background (verified)
- Facade = `oxdock` crate re-exports + `Engine<P: ProcessManager>` in `crates/oxdock-core/src/exec/engine.rs:174` (`register_module`, `register_type`, `run_script`, `run_steps_on`). No dynamic plugin loading exists; extension = `HostModule{name, funcs, types}` (`crates/oxdock-core/src/exec/native.rs:662`) built from `#[oxdock_func]` / `#[oxdock_type]` (`crates/oxdock-func-macro/src/lib.rs`).
- Bridge template = `crates/oxdock-core/src/exec/net_bridge.rs` (LISTEN/CONNECT): `require_async` + `WITH_IO stdin/stdout` ambient pipes, `SUPERVISOR_TICK`/`WORKER_BACKSTOP` 10ms pump, `CHUNK` 8192, `force_close`, cancel-token cascade. Reuse this shape; replace `TcpStream` with the SSH channel byte source/sink.
- Host ctx = `StepCtx<P>` (`crates/oxdock-core/src/exec/steps.rs:310`): `get_var/get_env/cwd/new_pipe/pipe_reader/pipe_writer/close_pipe` are public; but `state`, `cancel_token` (`state.rs:55`), and `out_pipe`/`stdin_pipe` (`steps.rs:322-327`) are `pub(super)` and **inaccessible to an external plugin crate**. net_bridge reads them directly (`net_bridge.rs:439,461`) because it lives inside core. The plugin cannot. All cross-crate stream/EOF/cancel access must go through public `StepCtx` methods (existing or newly added).
- Guardrails (`AGENTS.md`, `clippy.toml`, `deny.toml`): no raw `std::process::Command` / `std::fs` / `PathBuf` / `tempfile` / `UnguardedPath` in the plugin (only `crates/sys/*` get blanket allows; use narrow item-level `#[allow]` only if needed); no `cfg!(...)` macro (disallowed-macros `std::cfg`); no `_`-prefixed params; parity Linux/macOS/Windows; `indoc` for multiline test strings; every Rust fence must be a runnable doctest built with `oxdock!` (except parse-failure demos); READMEs generated by `docs-gen`, never hand-edited.

### 2. Public API (in `crates/plugins/oxdock-ssh-plugin/src/`)
- `lib.rs`: `pub fn module() -> HostModule<DefaultProcessManager>` plus generic `pub fn module_with<P: ProcessManager>() -> HostModule<P>` (keep `ProcessManager`-generic like all host modules; see `docs-gen/src/host.rs` pattern). Re-export opaque types.
- `types.rs`:
  - `#[oxdock_type(name="SSH_SERVER")]` struct `SshServerTag` wrapping `Arc<SshServerInner>` (`id: String`, `local_addr: SocketAddr`, shutdown trigger). `Clone+PartialEq+Display+Debug+Send+Sync` per macro requirements; `PartialEq` on id, `Display` redacts secrets (print `SSH_SERVER(id, addr)`, never user/password).
  - v1 credential passing: plain `STRING` args (`username: String`, `password: String`), empty password means auto-generate ephemeral (alphanumeric, 24 chars) and return it once in the result MAP. Do not mint a separate `SSH_CREDENTIALS` type in v1.
- `funcs.rs` (all `#[oxdock_func]`, module `SSH`):
  - `SSH_SERVE(cx, bind: String, username: String, password: String) -> MAP`: validates bind (`127.0.0.1:PORT`/`localhost:PORT`/`[::1]:PORT`; allow port `0` for ephemeral unlike `LISTEN`, then report actual addr; reject non-loopback), generates host key in memory (Ed25519 per call, never written to disk, so no `oxdock-fs` interaction), spawns server thread with its own `tokio` runtime (see section 3), returns MAP `{server: SSH_SERVER, addr: STRING, username: STRING, password: STRING}`. Non-blocking.
  - `SSH_ACCEPT(cx, server: SSH_SERVER, in_pipe: PIPE, out_pipe: PIPE) -> MAP`: blocking **dequeue-next-session + pump-outer-leg** with **explicit PIPE args** (NOT ambient extraction). Rationale: built-in `LISTEN`/`CONNECT` bind ambient `WITH_IO` streams via engine-level `resolve_io_streams`/`with_io` dispatch (`handlers.rs:1430`); `#[oxdock_func]` hosts never receive ambient bindings (their `StepCtx.out/err` is whatever the call site installed, and `out_pipe`/`stdin_pipe` stay `None`). So callers pass the same handles explicitly, e.g. `LET $r: MAP = SSH::ACCEPT($server, $in, $out)`. Implementation uses only public API: `cx.pipe_reader(&in_pipe)` / `cx.pipe_writer(&out_pipe)` for byte streaming, `cx.close_pipe(&out_pipe)` to propagate channel EOF downstream (this is the `force_close` path; never touch `PipeInner` directly). **Must run inside `ASYNC`: enforce with an async-task check and bail otherwise, mirroring `require_async`. Consequence: the proxy accept loop is a pool of `ASYNC` workers (see 3d), NEVER a serial `WHILE` with `ACCEPT` on the main flow (that would both trip the bail and serialize all clients behind one channel lifetime).**
  - `SSH_CLOSE(cx, server: SSH_SERVER) -> BOOL`: triggers graceful shutdown (stop accept, close sessions, join thread with timeout), idempotent. Best-effort companion to RAII teardown (see section 3).
  - `SSH_CONNECT(cx, target: STRING, username: STRING, password: STRING, in_pipe: PIPE, out_pipe: PIPE) -> MAP` (outbound, for the proxy use case): `russh::client` connection to `target` (`host:port`, any host unlike loopback-only `SERVE`) with **inner credentials fully independent of the outer `SERVE` creds**, channel shell/exec attached to the explicit pipes with the same direction convention as `ACCEPT` (client/wire bytes readable from `out_pipe`, DSL writes into `in_pipe`). **Blocking leg-pump until the channel closes; runs in its own `ASYNC` task CONCURRENT with the `PUMP` tasks (see 3d). Never sequence `CONNECT` before spawning `PUMP`s: `CONNECT` only returns at channel teardown, so pumps spawned after it would never exist and the session would deadlock waiting for bytes no one forwards.** v1 password-only; key auth is a follow-up (key path via `GuardedPath`, never raw `PathBuf`). Reuses the same runtime-thread + bounded-queue bridge as the server side.
  - `SSH_PUMP(cx, from_pipe: PIPE, out_pipe: PIPE) -> INT` (pipe-to-pipe copy, one direction): blocking byte copy with `cx.pipe_reader(&from_pipe)` / `cx.pipe_writer(&out_pipe)` until EOF or cancel, then `cx.close_pipe(&out_pipe)` so the far side sees EOF. This is the primitive the blueprint calls `PIPE_PUMP`: no such DSL builtin exists, and none is needed. A proxy spawns two per-client `ASYNC` tasks (one per direction). Returns byte count. **Read loop MUST use timeout-bounded reads (`cx.pipe_backend(&from_pipe)` + `read_into_timeout` with a ~10ms backstop, polling `is_cancelled()` each tick, mirroring `net_bridge::read_pipe`/`WORKER_BACKSTOP`): a bare blocking `Read::read()` on `SharedInput` would sleep through `TIMEOUT`/`CANCEL` on silent-but-open pipes and leak the task thread. See 3b.**
- Pipe direction convention (fixed for all four funcs): `out_pipe` carries bytes **produced by the wire side** (DSL reads: client keystrokes / server responses); `in_pipe` carries bytes **consumed by the wire side** (DSL writes). So `SSH::ACCEPT($srv, $c_in, $c_out)` then reading `$c_out` yields what the outer client sent.
- Wiring: `HostModule { name: "SSH".into(), funcs: vec![SshServe::registration(), SshAccept::registration(), SshClose::registration(), SshConnect::registration(), SshPump::registration()], types: vec![SshServerTag::descriptor()] }`.

### 3. Server runtime (`server.rs`, `auth.rs`, `bridge.rs`)
- Threading: `SSH_SERVE` spawns one `std::thread` per server owning a `tokio::runtime::Builder::new_current_thread().enable_all().build()` (or `new_multi_thread` with 2 workers if current-thread bridging proves awkward; document choice). No tokio types leak into `oxdock-core`; the thread boundary speaks only bounded channels plus `SharedInput/SharedOutput` handles captured from explicit PIPE args at `SSH_ACCEPT` time.
- Registry without leaks or stranded waiters: process-wide registry holds `Weak<SshServerInner>` (not `Arc`), keyed by server id; `SSH_ACCEPT`/`SSH_CLOSE` upgrade-or-bail (`bail!("SSH server closed")` on dead weak). Session queue is `Mutex<QueueState> + Condvar` where `QueueState { sessions: VecDeque<PendingSession>, shutdown: bool }`. Teardown contract (BOTH `SSH_CLOSE` and `SshServerInner::Drop`): poison-tolerant lock (never `try_write`-skipped: a skipped wakeup strands waiters, so use `lock().unwrap_or_else(|e| e.into_inner())`), set `shutdown = true`, then `condvar.notify_all()` while holding no other locks; never join threads or block in `Drop`. `SSH_ACCEPT`'s dequeue is a predicate loop (`wait_timeout` ~10ms ticks) that returns-or-bails on `shutdown == true` and polls `is_cancelled()` each tick, so close/drop/cancel always wakes every waiter. The runtime thread self-reaps on shutdown. Default bind allows port `0` (ephemeral) with the actual addr returned, so leaked-port collisions are structurally unlikely; loopback-only binds are still enforced.
- `auth.rs`: `struct EphemeralHandler { expected_user: String, expected_pass: String, session_tx: mpsc::Sender<...> }` implementing `russh::server::Handler`; `auth_password` compares in constant-ish time and returns `Auth::Accept/Reject`; no OS/PAM/`/etc/shadow` lookup. Log only `user` + accept/reject, never the password.
- `server.rs`: `russh::server::run` on loopback `TcpListener` (bind via tokio net inside the runtime thread); per connection spawn handler; on `channel_open_session` + `channel_req_shell`/`channel_req_exec`, package the channel handle + requested command and push to the session queue for the next `SSH_ACCEPT` call. Shell and exec both map to the same byte pump in v1 (exec command string surfaced in the `SSH_ACCEPT` return MAP; actual execution is whatever the DSL pipes do, not a local shell spawn).
- `bridge.rs`: mirror `net_bridge::pump/pump_in/pump_out` supervision shape (`std::thread::scope`, tick-reap, first-error-wins, cancel cascade) but with explicit `SharedInput/SharedOutput` handles (no `TcpStream`, no ambient `out_inner`). Sync/async handoff uses **bounded `tokio::sync::mpsc` byte-chunk queues** between russh callbacks and the sync pump threads; never run blocking pipe reads inside `spawn_blocking` on the tokio pool. EOF propagation: channel EOF -> `cx.close_pipe(&out_pipe)` so downstream observes EOF despite keeper pins; stdin-pipe EOF -> channel EOF/close. Cancellation: pump loop polls a cancel flag each tick (see core addition below); on cancel, shut both directions and return.
### 3b. Minimal `oxdock-core` additions (required; code-review driven)
The plugin cannot live on existing public API alone. Add the smallest possible surface in `crates/oxdock-core/src/exec/steps.rs` (blast radius: `StepCtx` has ~130 in-crate callers; pure getters, no behavior change):
- `pub fn is_cancelled(&self) -> bool` (reads `self.state.cancel_token`) so blocking pumps can exit on `TIMEOUT`/`CANCEL` without touching `pub(super)` state.
- `pub fn pipe_backend(&self, value: &Value) -> Option<Arc<PipeInner>>` resolving an **explicitly passed** `PIPE` value to its script backend (`value.as_pipe_handle()` + `oxdock_pipe::script_backend`, the same lookup `close_pipe` already uses internally; `None` for unbound/OS pipes). This MUST be value-based, NOT ambient `stdin_pipe_backend()`/`out_pipe_backend()` getters: `StepCtx.stdin_pipe/out_pipe` are populated only by engine-level `WITH_IO` resolution (`handlers.rs:1430`), which never runs for `#[oxdock_func]` calls, so ambient getters would return `None` inside `ACCEPT`/`CONNECT`/`PUMP` and the backstop would silently never engage.
These are REQUIRED (not optional) for all three blocking funcs (`ACCEPT`, `CONNECT`, `PUMP`): every pipe-read loop runs `read_into_timeout` with a ~10ms backstop on the resolved backend and polls `is_cancelled()` each tick, exactly like `net_bridge::read_pipe`/`WORKER_BACKSTOP`; `None` backends (OS/unbound pipes) fall back to blocking reads. A bare blocking `Read::read()` on `SharedInput` would sleep through cancellation on silent-but-open pipes and leak the task thread (SEV-2). The plugin names `PipeInner`/`read_into_timeout` via a direct `oxdock-pipe.workspace=true` dep (already a workspace member); if core owners prefer zero new type exposure, the fallback is a `pub fn read_pipe_timeout(&self, value: &Value, buf: &mut [u8], timeout: Duration) -> io::Result<Option<usize>>` helper encapsulating the same lookup+read, but the polling guarantee itself is non-negotiable.
No other core changes: no grammar, no `LISTEN`/`CONNECT` edits, no `PipeInner` exposure beyond the above.
### 3c. Multi-client concurrency (one pipe pair per session, no shared-pipe multiplexing)
Raw OxDock pipes are unframed byte streams: two sessions writing into one pipe interleave bytes with no session boundary, so v1 explicitly does NOT multiplex clients over a single pipe. Concurrency model:
- Server side keeps a thread-safe session queue (`Mutex<QueueState> + Condvar` with `shutdown` flag and notify-all teardown per section 3; NOT `std::sync::mpsc`, which is single-consumer and cannot serve concurrent `ACCEPT` calls). Each authenticated connection enqueues one `PendingSession` (bounded tokio mpsc byte channels + exec-request metadata).
- Each client gets its own `ASYNC` task running `SSH::ACCEPT($server, $in, $out)` with a **dedicated pipe pair** (`LET $in: PIPE`, `LET $out: PIPE` per task iteration). Concurrent `ACCEPT` calls pop distinct sessions FIFO; N simultaneous clients = N `ACCEPT` tasks + N pipe pairs.
- Sequential reuse of one pipe variable across sessions is allowed only strictly serially (session disconnects, EOF propagates via `close_pipe`, handles released) and preferably with freshly declared pipes per iteration (OS-materialized handles are take-once; script pipes carry keeper semantics).
- Canonical shape (docs + doctest; `WHILE` takes a bare bool-expr, counters via bare reassignment per the note in 3d):
  `LET $run: BOOL = true`
  `WHILE $run { ASYNC { LET $in: PIPE; LET $out: PIPE; LET $r: MAP = SSH::ACCEPT($server, $in, $out); ... } }`
- Framed multiplexing (TLV / channel-ID headers over one pipe) is an explicit non-goal for v1; if ever needed it becomes a separate versioned framing layer, never implicit interleaving.
### 3d. Proxy pattern (outer creds -> inner SSH with different auth)
1. Outer auth: `SSH::SERVE(bind, outer_user, outer_pass)` — one credential pair per server instance (multiple outer identities = multiple `SERVE` calls on different ports; a user:pass map is a possible follow-up, not v1). Ephemeral by construction: creds live in memory, server vanishes with the process.
2. Worker-pool shape (NOT serial main-thread accept): a bounded pool of `ASYNC` workers (pool size = max concurrent clients) each loops over fresh pipe pairs. Within one worker iteration all four legs run **concurrently**: the inner `CONNECT` leg and both `PUMP`s are spawned as child `ASYNC` tasks FIRST (they idle-block on empty pipes, which is fine), then the worker itself calls blocking `ACCEPT` (dequeues the next session and pumps the outer leg until close), then awaits the children. Corrected canonical shape:
  `LET $server: SSH_SERVER = SSH::SERVE("127.0.0.1:2222", $outer_user, $outer_pass)`
  `LET $w: INT = 0`
  `WHILE $w < 4 { ASYNC {`
  `  LET $run: BOOL = true`
  `  WHILE $run {`
  `  LET $c_in: PIPE; LET $c_out: PIPE; LET $i_in: PIPE; LET $i_out: PIPE`
  `  LET $h_inner: HANDLE = ASYNC { SSH::CONNECT($target, $inner_user, $inner_pass, $i_in, $i_out) }`
  `  LET $h_p1: HANDLE = ASYNC { SSH::PUMP($c_out, $i_in) }`
  `  LET $h_p2: HANDLE = ASYNC { SSH::PUMP($i_out, $c_in) }`
  `  LET $sess: MAP = SSH::ACCEPT($server, $c_in, $c_out)`
  `  AWAIT $h_inner; AWAIT $h_p1; AWAIT $h_p2`
  `  } }; $w = $w + 1 }`
  Syntax notes (all fences in this repo are runnable doctests, so CI proves every sketch): `WHILE` takes a bare bool-expr (`WHILE <bool-expr> {`, `commands.rs:2144`; `[]` is a list literal and never valid there); loop counters use bare reassignment (`$w = $w + 1`, as in the `WHILE !$done { $done = true }` integration test) because `while_loop` pushes a fresh scope per iteration (`handlers.rs:1892`) and a `LET` re-declare would be dropped at scope pop, looping forever.
  Why this order: `ACCEPT`/`CONNECT` only return at channel teardown, so anything sequenced after them without concurrency never runs (the SEV-1 deadlock). Spawning legs first lets each direction flow as soon as its peer arrives.
3. Direction check: outer client keystrokes arrive on `$c_out` -> pumped into `$i_in` (consumed by inner server); inner responses arrive on `$i_out` -> pumped into `$c_in` (consumed by outer client). EOF cascade tears down the whole per-client set without orphans: outer disconnect -> `ACCEPT` returns + `close_pipe($c_out)` -> `PUMP($c_out->$i_in)` sees EOF, closes `$i_in` -> `CONNECT` leg sees stdin EOF, half-closes inner channel -> inner EOF -> `CONNECT` closes `$i_out` -> `PUMP($i_out->$c_in)` sees EOF, closes `$c_in` -> all four tasks join the `AWAIT`s and the worker loops back to `ACCEPT`.
4. Warm-standby tradeoff (documented, accepted for v1): idle workers dial their inner connection before any outer client arrives, so pool size N means up to N idle inner sessions. This bounds resource use and keeps the script deadlock-free; a future `SSH_NEXT`-style dequeue/pump split could dial lazily if idle sessions ever become unacceptable.
5. Alternative without a new outbound primitive (`RUN ["ssh", ...]` via `oxdock-process`) is deliberately NOT the v1 path: it shells out through `CommandBuilder`, inherits host keys/`known_hosts` behavior, and differs per OS. Native `SSH::CONNECT` keeps both legs inside the plugin's russh runtime with identical behavior on Linux/macOS/Windows.
6. Secrets discipline: outer and inner creds travel as `STRING` args from `INHERIT_ENV` (e.g. `INHERIT_ENV [SSH_OUTER_PASS, SSH_INNER_PASS]`) + `[env:K]` guards; never logged; `Display`/`Debug` on all SSH types redact.
- No `std::process::Command`, no PTY, no `ssh` subprocess in v1 (that hop design is explicitly out of scope). No filesystem writes (host key in memory), so `clippy.toml` denies are naturally satisfied.

### 4. Validation, secrets, errors
- Endpoint/auth validation errors shaped like `net_bridge` (`step N: SSH_SERVE ...` via anyhow context; pure-string checks, Miri-safe).
- Secrets: encourage `INHERIT_ENV [OXDOCK_SSH_PASS]` + `[env:K]` guards in docs/doctests; never log password or host-key material; `Debug` impls redact.

### 5. Tests
- Unit (no network): bind validation, credential generation length/charset, `Display`/redaction, duplicate-module registration panic parity.
- Integration (loopback, ephemeral ports with discovery via return MAP; `#[cfg_attr(miri, ignore = "needs loopback TCP + threads + tokio runtime")]` with reason): serve with known creds, wrong-password rejected, `ASYNC { LET $r: MAP = SSH::ACCEPT($server, $in, $out) }` round-trips bytes through a real `russh` client (add `russh` client + `tokio` to dev-deps, loopback only) with explicitly passed pipes, channel disconnect propagates EOF via `close_pipe` (downstream reader test asserts EOF, no deadlock), `TIMEOUT`/`CANCEL` unblocks the pump via `is_cancelled`, `SSH_CLOSE` idempotent and handle-drop does not leak the port (bind-twice test).

## Non-goals for v1
Subprocess hop (`ssh destination@host` via `RUN`, with host `known_hosts`/agent behavior), public-key auth, SFTP/subsystem support, new DSL syntax commands, `LISTEN`-style explicit-port-only restriction (plugin returns the ephemeral addr instead), PTY resize/raw modes, multi-credential maps per server, framed single-pipe multiplexing.

## Risks
- tokio inside a sync workspace: contained by the one-thread-per-server boundary, but adds compile weight and a second I/O runtime to audit. Mitigation: minimal tokio features, no tokio in public API.
- russh API churn + license transitive closure: pin exact versions, gate on `cargo deny`.
- `SSH_ACCEPT` server-handle routing across `ASYNC` task threads: v1 uses a process-wide registry (`RwLock<HashMap<server_id, ...>>`); keep ids unique (counter + random suffix) and document that two accepts on the same server serialize sessions FIFO.

## Verification
`cargo test -p oxdock-ssh-plugin`, then `cargo test --workspace --tests`, `cargo clippy --workspace -- -D warnings`, `cargo run -p docs-gen`, plus a manual loopback demo: serve ephemeral creds, connect with an SSH client, explicit-pipe echo script (`SSH::ACCEPT($server, $in, $out)`) receives bytes and replies, disconnect yields EOF downstream, `SSH_CLOSE` leaves no OS trace (no users, no config).
