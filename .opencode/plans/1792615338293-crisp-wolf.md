# Plan: Background Execution via Native ASYNC + STD::TASK_POLL (supersedes MCP_SPAWN/MCP_POLL)

## Goal
Purge the transport-layer background machinery (`JobTable`, `_background` already gone, `MCP_SPAWN`/`MCP_POLL` synthesized tools) and replace it with the engine-native model: scripts detach with `ASYNC` blocks and return the `HANDLE`; `HANDLE` crosses the MCP JSON boundary as `{"task_id": N}`; new `STD::TASK_POLL($task: HANDLE) -> MAP` reports running state, partial tails, and final outcome. No second concurrency model, no RPC intercepts, no `BG_SPAWN`, no `RUN --background` flag (ASYNC blocks already detach; a flag would duplicate the mechanism).

## Locked decisions (review verdict + user direction)
- Return/param type is `HANDLE` everywhere. No `BG_SPAWN` builtin: `ASYNC` is the spawner.
- `MCP_SPAWN`/`MCP_POLL`, `JobTable` (`core/src/exec/jobs.rs`), `SessionCancel`, envelope parsing, handler-owned table, per-spawn `McpSession::init` are all deleted. RPC dispatches blind.
- `CANCEL`/`AWAIT` keep var-only DSL syntax (no parser change). Cross-call cancel/await goes through exported wrapper `FUNC`s taking `HANDLE` params (Option A). In-script `CANCEL $t` / `AWAIT $t` work on detached handles unchanged.
- `POLL`-after-`AWAIT` errors like double-await. `TASK_POLL` never consumes; `AWAIT` afterwards still works.
- Live-stream forwarder stops on call end via a done flag, not channel disconnect: detached workers hold senders past the response, so waiting for disconnect would stall every backgrounded call until the job finishes. Queued chunks still drain first; nothing that arrived is lost.
- Finished-task memory is bounded automatically (review AMEND, Option A): at most 128 retained finished entries per session; the sweep triggers on every async allocation, named or anonymous, bound at the common task-allocation primitive so no path bypasses it. Spawning past the cap evicts the oldest finished entry and drops its tails. Running tasks are never evicted. No `TASK_FORGET`; reaping must not depend on agent discipline.
- Live-task concurrency is bounded by hard admission control (review AMEND, second round): at most 64 running tasks, enforced by a shared atomic counter with a per-worker RAII release guard (covers nested workers; per-state table scans would miss them). Spawning past the cap fails the step loudly instead of wedging the host. No silent kills, no unbounded queue. Anonymous spawns go through the same gate; cleanly-finished anonymous handles are purged on alloc while failed ones are kept for end-pipeline error reporting.
- Per-task output capture is new machinery: `TaskTails` ring on `TaskEntry`, 64 KiB per stream, head-drop, non-destructive snapshot. Not `SlidingWindow`/`ExactCapture` (wrong retention semantics), not `TailRing` (destructive, call-scoped).
- `RUN --background` is explicitly out of scope.

## Implementation order
1. Retire: delete `core/src/exec/jobs.rs`, strip `SessionCancel`/`cancel_handle`, delete MCP spawn/poll surface (server.rs methods/tools/branches/reservations, jobs.rs file, lib.rs wiring), update session.rs expectations (tool lists back to `["SOLO", "MCP_STATUS"]`-shape, delete background tests).
2. Boundary: `HANDLE` projects as `{"task_id": N}` object (distinct schema, self-documenting, no `INT` confusion, extensible). Tag-directed helpers enforce shape at the boundary; `value_to_json` itself also projects handles (deviation: script `FUNC`s have no declared return tag, so the untyped path must project or no script tool could ever return a handle). `json_to_value` stays lenient (a `{"task_id": N}` object without a `HANDLE` tag still decodes as MAP). All other opaque types stay rejected.
3. Capture + retention: `TaskTails` on `TaskEntry`, fan-out tee at ASYNC spawn, completion record (`ok`, `exit_code`, `result`, `error`) written once by first observer, read-only poll path.
4. `STD::TASK_POLL` in `native.rs` + registration + executing `#[example]` fences.
5. tools.oxdock: long tools wrap `RUN` in `ASYNC`, return the `HANDLE`; `EXPORT [STD::TASK_POLL]` (qualified export is proven).
6. Docs templates + `docs-gen` regen. Tests + clippy + fmt.

## TODO (follow-up): tool failures as `isError` content with stderr
Motivating case: `RUN ["vaultclone", "push", ...]` exited 1 and the MCP caller got `-32603` with the command plus `exit status: 1` but zero bytes of the child's stderr. Indistinguishable from a server bug, nothing to diagnose or retry on.

MCP already has the right shape: `CallToolResult` carries an `isError` flag alongside `content`. Convention per spec and SDKs:
- Protocol errors (`-32603` etc.): the machinery broke. Bad args, server bug, transport failure. No tool logic ran.
- `isError: true` results: the tool ran and failed. Command failed, assertion tripped, file missing. Content carries the diagnosis and stays in a form the model can reason about and act on.

oxdock currently collapses both into `-32603`. Two-part fix:
1. Plumbing: capture the child's stderr into the failure (bounded tail, same truncation discipline as the stdout sinks).
2. Shape: return tool-logic failures as `isError: true` content (command, exit code, stdout tail, stderr tail) instead of JSON-RPC errors. Reserve `-32603` for actual machinery breakage.
Goal shape: "exit 1, stdout was X, stderr was Y". A code and the story, usable by the caller.
Routing principle (user-stated): MCP mode must not change output routing semantics. Step stdout/stderr flow to the MCP layer by default, streamed live (same as CLI prints live to the terminal). Explicit `WITH_IO` redirections override per-step in both modes identically. No opt-in to see output; no separate behavior under MCP. Channel: progress notifications when the client sends a progressToken (standards-clean, content in `message`, byte count as progress; no deprecated API), `notifications/message` fallback otherwise (deprecated by SEP-2577; isolated to the fallback branch so a future rmcp removal only costs token-less streaming, never a fork). Each chunk goes out exactly once, on the best available channel. Final result carries only the return value (no output replay); failure messages carry stdout/stderr tails.

## Code review verdict (pipe-stringification fix): AMEND
Review of the in-flight `format_value_for_string -> Result` change (pipe refusal with remediation). Verdict: amend, one SEV-2 flaw.

Flaw: the guard covers only `PIPE`. `SEMAPHORE` and `PERMIT` are equally opaque host types and fall through to `format!("{}", val)`, silently stringifying. Same gap applies inside containers (`LIST`/`MAP` recursion rejects pipes but would pass semaphores/permits through). Fix narrows diagnostics to one opaque family while leaving the identical bug open for concurrency primitives.

Directive: reject all opaque types uniformly in `format_value_for_string` (`crates/sys/oxdock-process/src/expand.rs`). Accessors verified present (`value.rs:626 as_semaphore`, `:633 as_permit`, `:698 as_pipe_handle`). Add semaphore/permit arms alongside the pipe arm, each with family-appropriate remediation text (capture-output guidance fits pipes; semaphores/permits need their own wording, not a copy-paste).
Open scope question for implementation: the sibling guards added in the same change (`coerce_scalar` pipe arm in `core/src/exec/args.rs`, `flatten_exec_value` pipe arm in `core/src/exec/handlers.rs`) have the identical single-family gap. Extend the uniform rejection there too, or justify the narrower scope. Do not expand to `HANDLE` (`task#id` rendering) without a separate decision.
