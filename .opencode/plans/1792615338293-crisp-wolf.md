# Plan: MCP Tool Hosting for Exported Script Functions (#153, full implementation)

## Goal
Implement everything needed for `oxdock --mcp script.oxdock` end to end: single-file `EXPORT` support to drive the tool table, new `oxdock-mcp` crate owning the MCP reactor on `rmcp`, thin `oxdock-cli --mcp` wrapper behind an opt-in feature flag, plus a small self-documenting demo script provable from OpenCode. Lock in with integration tests after the demo works.

Source: https://github.com/jzombie/rust-oxdock/issues/153 (body + 10 comments, esp. remote-binding/topology notes, rmcp suggestion, fast-track correlation comment).

## User decisions (locked)
- Packaging: new workspace crate `crates/oxdock-mcp` owns JSON-RPC loop, tool-table derivation, Value-to-JSON boundary. `oxdock-cli` re-exports it as a thin wrapper so there is still one `oxdock` binary. Gated by `mcp` feature flag, off by default, on under `all-features` / published full feature sets.
- Transport: use `rmcp` crate. Expose at workspace level (`[workspace.dependencies] rmcp`), import inside `oxdock-mcp`.
- EXPORT scope: single-file `EXPORT [A, B]` list only in this ticket. Full file-based `IMPORT` module loading + purity stays in #115. Leave a comment on #115 stating this (implementation step, via `gh issue comment 115`, not done in plan mode).
- Example: small demo script proving tools/list + tools/call from OpenCode, functions self-document. Integration/CLI tests come after the demo works.

## Implementation plan

### 1. Single-file EXPORT (parser + runtime)
Files: `crates/oxdock-parser/src/dsl.pest`, `ast.rs`, `parser.rs` (`LowerCtx`, `lower_import_statement` area, `parse_block_elements_with_lower`), `commands.rs`, `core/src/exec/native.rs` (`define_script`, `FunctionRegistry`, `list_functions/describe_function/meta_to_value`), `core/src/exec/static_check.rs`, `crates/oxdock-parser/tests/integration/import.rs`, `crates/oxdock-logic-tests/fixtures/...` (new EXPORT cases).

- Syntax: `EXPORT [FOO, BAR]` and `EXPORT FOO` (single + bracket list). Bare uppercase idents, comma separated, same line. Reject: guarded `EXPORT` (mirror `IMPORT cannot be guarded`), block-scoped `EXPORT` (top-level only, mirroring module semantics), unknown names, duplicates, non-FUNC names, qualified `MOD::X`. Keep `export_statement` pest shape but replace `(!linebreak !";" ANY)*` tail with a real ident-list rule so lowering gets names + spans.
- Lowering: add `LowerCtx.exports: Vec<String>` (or HashSet + order vec). `EXPORT` updates the set, emits no `Step` (like `IMPORT`). Validate each name resolves via `visible_func_names()` / `declare_func` table at EXPORT site; forward references allowed so validate again at end of `lower()` (collect-then-check, same as Phase-A `static_check collect()` pattern). Cross-check with `FuncDef` collection so `EXPORT` after/before `FUNC` both work.
- Init semantics (amended per review): MCP loader parses the script, then executes top-level steps sequentially to build a fully initialized `ExecState` (globals, `LET`, `WORKSPACE`, `ENV`, function definitions). Only after linear execution succeeds does it validate the `EXPORT` list and hand the resulting state to the reactor. Never discard linear steps. Document that this runs top-level side effects once at startup as the price of correct ambient scope until #115 purity lands.
- Runtime: track export set from parser into `Engine`/`ExecState` (e.g. `Engine::parse_script_with_exports` returns `(steps, exports)` or a `HostModule`-named table). `define_script` stays `SCRIPT::NAME`; add `FunctionRegistry::exported()` / `list_exported(exports)` view. `FUNCTIONS()`/`DESCRIBE()` unchanged; MCP reads `FuncMeta` directly (not via `meta_to_value`, which blanks param docs per `native.rs:2828-2919`).
- Script FUNC docs (amended per review, no global lexer change): do not thread `#` through `RawToken` globally. Instead add a narrow `doc_comment` pest rule matching only the immediate-predecessor comment block above `func_def`, extract it in `lower_func_def_from_pair` into `FuncMeta.summary` (first line) + `docs` (full block). All other comments keep current discard behavior. Params keep `docs:""`; `returns` stays `None` unless trivial to add `-> TYPE` later.
- Update `export_is_reserved` test to assert new behavior; add `export_unknown_name`, `export_guarded_rejected`, `export_duplicate`, `export_list_order` cases.

### 2. New crate `crates/oxdock-mcp`
Files (new): `crates/oxdock-mcp/Cargo.toml`, `src/lib.rs`, `src/schema.rs`, `src/tools.rs`, `src/reactor.rs`, `src/io.rs`, `tests/*`, `.oxdock/template/` + `target.json`/`values.json` + `fragments/overview.md.tmpl` (per repo docs-gen rule: every crate ships a pipeline README with one runnable `oxdock` fence), plus workspace `Cargo.toml` members + `[workspace.dependencies] rmcp`, `docs-gen.json` scope if needed.

- Deps: `rmcp` (workspace-level, version resolved at implementation via crates.io, e.g. `cargo add` dry-run first), `serde/serde_json/anyhow`, `oxdock-core`, `oxdock-parser`, `oxdock-fs`, `oxdock-process`, `tokio` (stdio transport needs `rt` at minimum; reuse workspace feature set).
- Tool-table derivation (`tools.rs`): `build_tool_table(registry, exports) -> Vec<McpTool { name: BASE, qualified: SCRIPT::BASE, meta }`. Names exposed to MCP are bare base names (deduped, must be unique). Keep qualified name internally for `call_func_value`.
- JSON Schema emitter (`schema.rs`): `TypeTag -> JSON Schema` for params + return. `params: Option<Vec<FuncParam>>` becomes `{type:object, properties:{...}, required:[...]}`. Mapping: `String->string, Int->integer, Float->number, Bool->boolean, List->array, Map->object, ListOf(t)->{array,items:schema(t)}, MapOf(t)->{object,additionalProperties:schema(t)}, Record(fields)->{object,properties,required}`, `Union->anyOf`, `Any/None->{}`, `allowed->[enum]`, `options` (MAP keys) -> nested properties, `optional` trailing MAP -> omit from required. `Pipe/Handle/Duration/Path/Semaphore/Permit/Custom(opaque)` -> validation error naming the type (fail before reactor opens, per issue section 3). Reuse `value_to_json`/`json_to_value` in `args.rs` for the value boundary; add `json_to_value_checked(json, TypeTag)` enforcing `check_value_at`-equivalent coercion + `fill_optional_args` + arity gate.
- Reactor (`reactor.rs`): `serve_stdio(engine, exec_state, tool_table)` event loop. `initialize` -> advertise `tools/list`, `tools/call`. `tools/list`: project `FuncMeta.summary/docs/params` to `{name, description, inputSchema}`. `tools/call`: parse JSON args object -> ordered `Vec<Value>` per `FuncParam` order (missing optional trailing MAP fills `{}`; missing required errors) -> `call_func_value` within the persistent initialized `ExecState` -> `value_to_json` -> MCP `content: [{type:text, text: json_string}]`. Per-call I/O hygiene: extract captured stdout/stderr into the response `content`, then immediately truncate both `Vec` sinks to length zero before the next request (no unbounded growth). Errors become JSON-RPC errors with `call_func_value` message, never panics. Fail-fast: tool-table derivation rejects opaque params/returns (`PIPE/HANDLE/SEMAPHORE/PERMIT/Custom`, plus `PATH/DURATION` per `value_to_json` limits) at startup and crashes `oxdock --mcp` before the reactor opens, never proceeding to serve.
- Stdio framing (`io.rs`): on entering MCP mode, reconfigure `ExecIo`: `set_stdout`/`set_stderr` to in-memory `SharedOutput` Vec sinks (never inherit, never `io::stdout()`). `ECHO` then lands in the capture; after each call, captured stdout text is appended as a second `content` text block (or empty if none), then buffers are cleared per above. `RUN` children: force `CommandStdout/Stderr::Stream(captured)` so no child writes touch process stdout; diagnostics/logging go to process stderr only. Refuse to start when stdin/stdout is a TTY (mirror `serve.rs:130-183` guard). Large outputs: rely on existing `EXACT_STDOUT_CAP=8MiB`; truncate with a `truncated:true` annotation rather than breaking framing.
- No conversation logging in this ticket (issue comments discuss LOG_TAIL/JSONL; explicitly out of scope; reactor keeps no log file).

## Risks / open points
- `rmcp` API version unknown until implementation; if its stdio server fights our `ExecIo` ownership, fall back to hand-rolled `serde_json` line loop inside `oxdock-mcp` behind the same `serve_stdio` signature (CLI unaffected).
- Persistent `ExecState` across calls vs stateless tools debate in comments: issue body mandates persistent state; keep the executed-at-startup state for the session (amended: execute linear steps once, then persist), since script `FUNC`s may use vars/scopes. Note statelessness as follow-up if the knowledgebase consumer demands it.
- Memory: per-call truncation of `SharedOutput` Vec sinks is load-bearing; add a regression test issuing N sequential calls with ECHO output and asserting sink length stays bounded (zero after drain) plus RSS sanity.

## TODO (follow-up): tool failures as `isError` content with stderr
Motivating case: `RUN ["vaultclone", "push", ...]` exited 1 and the MCP caller got `-32603` with the command plus `exit status: 1` but zero bytes of the child's stderr. Indistinguishable from a server bug, nothing to diagnose or retry on.

MCP already has the right shape: `CallToolResult` carries an `isError` flag alongside `content`. Convention per spec and SDKs:
- Protocol errors (`-32603` etc.): the machinery broke. Bad args, server bug, transport failure. No tool logic ran.
- `isError: true` results: the tool ran and failed. Command failed, assertion tripped, file missing. Content carries the diagnosis and stays in a form the model can reason about and act on.

oxdock currently collapses both into `-32603`. Two-part fix:
1. Plumbing: capture the child's stderr into the failure (bounded tail, same truncation discipline as the stdout sinks).
2. Shape: return tool-logic failures as `isError: true` content (command, exit code, stdout tail, stderr tail) instead of JSON-RPC errors. Reserve `-32603` for actual machinery breakage.
Goal shape: "exit 1, stdout was X, stderr was Y". A code and the story, usable by the caller.
Routing principle (user-stated): MCP mode must not change output routing semantics. Step stdout/stderr flow to the MCP layer by default, streamed live via `notifications/message` (same as CLI prints live to the terminal). Explicit `WITH_IO` redirections override per-step in both modes identically. No opt-in to see output; no separate behavior under MCP.

## Code review verdict (pipe-stringification fix): AMEND
Review of the in-flight `format_value_for_string -> Result` change (pipe refusal with remediation). Verdict: amend, one SEV-2 flaw.

Flaw: the guard covers only `PIPE`. `SEMAPHORE` and `PERMIT` are equally opaque host types and fall through to `format!("{}", val)`, silently stringifying. Same gap applies inside containers (`LIST`/`MAP` recursion rejects pipes but would pass semaphores/permits through). Fix narrows diagnostics to one opaque family while leaving the identical bug open for concurrency primitives.

Directive: reject all opaque types uniformly in `format_value_for_string` (`crates/sys/oxdock-process/src/expand.rs`). Accessors verified present (`value.rs:626 as_semaphore`, `:633 as_permit`, `:698 as_pipe_handle`). Add semaphore/permit arms alongside the pipe arm, each with family-appropriate remediation text (capture-output guidance fits pipes; semaphores/permits need their own wording, not a copy-paste).
Open scope question for implementation: the sibling guards added in the same change (`coerce_scalar` pipe arm in `core/src/exec/args.rs`, `flatten_exec_value` pipe arm in `core/src/exec/handlers.rs`) have the identical single-family gap. Extend the uniform rejection there too, or justify the narrower scope. Do not expand to `HANDLE` (`task#id` rendering) without a separate decision.
