# Plan: Remote Execution Context (issue #158)

## Goal
`REMOTE <target> [...] { ... }` blocks execute sealed from outer scope on
a remote guest running its own OxDock binary. Guest self-provisions (host
never builds or ships guest binaries). Transport is any stdio command
(sshd, local binary, `docker exec -i`, `kubectl exec -i`, `wsl`) framed
with `muxio` (crates.io, v0.16 alpha line). Core owns the block
primitive; everything remote lives behind the NET plugin.
Toolchain-plugin work from #179 is shelved and out of scope.

## Locked decisions (from owner)
- Closed scope, in the keyword: no variables cross except header-listed
  names. `WITH_IO` pipe bindings plus declared file transfers are the
  sole communication.
- NO bulk workspace sync, ever. The guest starts EMPTY. Files cross only
  through explicit `COPY --from-host` / `--to-host` declarations visible
  in the script. Unflagged `COPY`/`READ`/`RUN` inside `REMOTE` are
  guest-local against the empty staging workspace.
- Target-only in scripts. No transport vocabulary in the DSL. Host
  inventory binds targets at startup, fail-fast, with resolution logging.
  Same posture as the `EndpointRegistry` built from
  `--listen`/`-p`/`--offline`.
- OS-facilitated transports only (system `ssh` binary et al), never russh.
  OxDock owns framing, not auth.
- Per-command RPC is rejected. Protocol is block-granular: transfers are
  declared in the block header/body and fulfilled proactively around
  execution (no FETCH/PUSH request/response round-trips); new DSL
  commands work remotely automatically with zero protocol changes.
- Text is the shippable unit (`Display` round-trip already guaranteed).
- Host wins on partition. Stream close equals cancel.
- Core primitive, NET-provided sessions: without the NET plugin, `REMOTE`
  bails with an actionable error.

## DSL shape: `REMOTE` with header binding list
- New `StepKind::RemoteBlock { target: String, vars: Vec<String>,
  env: Vec<String>, body: Vec<Step> }` in
  `crates/oxdock-parser/src/commands.rs`. `WORKSPACE` is untouched and
  `WorkspaceTarget` stays closed: the `WORKSPACE` prefix promised switch
  semantics this construct cannot honor. `REMOTE` states the act (run this
  block on that target); the header list states the data dependencies.
  No wrapper keywords, no nesting, no prefixes, no in-body declarations.
- Syntax:
  ```oxdock
  WORKSPACE LOCAL
  ECHO "do something on host"
  WITH_IO [stdout=$out] {
      REMOTE prod [$version, env:DEPLOY_ENV] {
          RUN ./deploy.sh $version
      }
  }
  # Host scope restored; READ files or $out for results.
  ```
  `REMOTE <target> [<bindings>] { ... }` takes a static-literal target,
  an optional bracket list, and a mandatory braced body. List entries are
  `$var` (outer `LET` variable, same-name injection) or `env:NAME`
  (outer env key); anything else bails at lower time, as do dynamic
  names. Empty and omitted lists are identical (fully sealed).
  Same-name injection only (renaming deferred, not v1). Canonical
  Display renders the header on one line and the body indented.
- Closed scope: nothing crosses except header-listed names, `WITH_IO`
  bytes, and declared `COPY` transfers. The block otherwise sees only
  guest-local environment, starting from an EMPTY staging workspace.
- Explicit file transfer via `COPY` direction flags (new `StepKind::Copy`
  fields `from_host: bool`, `to_host: bool`, mutually exclusive):
  `COPY --from-host <host-path> <guest-path>` fetches host paths into
  the guest staging dir before execution;
  `COPY --to-host <guest-path> <host-path>` pushes guest paths back to
  the host active root after successful execution. Paths are workspace
  relative on their respective sides and resolve under guard on both
  ends. Unflagged `COPY` inside `REMOTE` stays guest-local. The flags
  are valid ONLY inside `REMOTE` bodies (parse-time error otherwise, via
  a `LowerCtx` remote-depth counter). Transfers are unconditional
  declarations: hoisted around execution, so a guarded-out flagged COPY
  still transfers (documented; restructure into separate blocks when
  conditional transfer matters). Missing `--from-host` sources fail fast
  before execution; missing `--to-host` sources fail loudly after.
- Injection mechanics (no value protocol): at interception the host
- Injection mechanics (no value protocol): at interception the host
  resolves each listed name against its live scope, renders a `LET` /
  `ENV` declaration line, and prepends the lines to the shipped text, so
  the guest parses ordinary steps. Renderable set (tight v1): `STRING`,
  `INT`, `FLOAT`, `BOOL`, `DURATION`, and `LIST`/`MAP` composed solely of
  those, reusing the host declaration kind
  (`LET $version: STRING = "1.2.3"`). Rendering uses canonical DSL
  literal escaping, the exact inverse of runtime `expand_string`
  (`args.rs:893-897`): `\` to `\\`, `"` to `\"`, newline to `\n`, CR to
  `\r`, tab to `\t`, and `{{` to `\{{` (unescaped braces would
  interpolate guest-side). A dedicated `render_dsl_literal` helper owns
  this table (not the `quote_arg`/`quote_msg` Display helpers, which do
  not cover control characters); round-trip property tests assert
  parse(render(v)) == v, including hostile strings (quotes, backslashes,
  newlines, `{{ $x }}`, instruction-boundary `;`/`}`). Unknown names bail
  (`REMOTE 'prod' uses unknown variable $foo`); anything else (`PIPE`,
  `HANDLE`, `SEMAPHORE`, `PERMIT`, `PATH`, host opaque types) bails
  naming the variable (`cannot pass $p: PIPE into REMOTE 'prod' (pass
  bytes via WITH_IO, files via the workspace)`). A body `LET` over a
  passed name follows normal nested-scope shadowing (the body runs one
  scope deeper, like every braced block); deterministic and standard,
  not an error.
- `WITH_IO` is a byte channel like any other command: block form
  (`WITH_IO [...] { REMOTE ... }`) via parse-time expansion (zero parser
  changes, `parser.rs:940-954`) AND single-line prefix form
  (`WITH_IO [...] REMOTE t [...] { ... }`) via the generic `command`
  rule (same treatment `TIMEOUT` already enjoys). Ditto single-line
  `TIMEOUT <dur> REMOTE ...` and `ASYNC REMOTE ...`. `LET`-capture of
  `REMOTE` stays rejected (a sealed block produces no capturable value).
- Self-containment is AST-symbol only (never consults the runtime
  module table): lowering collects `DefineFunc` names declared outside
  the `RemoteBlock` vs inside it, walks the body for call nodes and
  call expressions, and bails only when a call matches an *outer
  user-defined* symbol and no inner one:
  `REMOTE 'prod' calls outer function 'build' (functions must be defined
  inside the block)`. Native `StepKind`s (`Echo`, `Read`, `Write`, ...),
  builtins, and `IMPORT`ed module functions pass untouched by
  construction: they are distinct variants/symbols, not `DefineFunc`
  nodes, so the check cannot misfire on them.
- The target is a static literal naming an inventory entry bound with
  `--remote`. Deferred or computed selection is not expressible (no
  `$var`, no `{{ }}`): the same script targets a different machine by
  rebinding inventory, never by editing. Unresolved target is a startup
  error after parse, before execution.
- Lowering validation: `^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$`; reserved words
  (`SNAPSHOT`, `LOCAL`, `CACHE`, `SYSTEM`, `REMOTE`) rejected.
- Guest-local semantics inside body: `WORKSPACE` selection, `COPY`, `RUN`
  resolve against guest roots and guest module table.
  Host `-p`/`--listen`/`--offline` never cross. `--offline` does not
  disable remote execution (outbound ssh stdio, no listening socket).
- `parse_script(Display) == original` must hold; add round-trip tests.
  Extend `test_lower_mock::lower` in lockstep.

## Boundary semantics
- Host resolves header-listed names against its live scope, renders
  `LET`/`ENV` lines, resolves `COPY --from-host` declarations against
  the host ACTIVE root (files plus recursive dirs, under guard),
  prepends injections to `body` text (`step.to_string()`), ships text
  plus fetch bytes in one `exec` stream. NO value payload. Guest parses
  with its own `parse_script_with_modules` and runs the full engine
  (`run_steps_with_lazy_snapshot_and_modules`). No per-command dispatch.
- The guest staging workspace starts EMPTY: a fresh temp dir per exec,
  populated only with fetched entries. No snapshot, no materialization,
  no host tree is ever walked for sync. Flagged `COPY` steps are transfer
  declarations fulfilled by the session (pre/post execution); the guest
  engine acknowledges them as no-ops when guest-mode is set (a session
  flag on the guest `Engine`, never set on hosts), so declared paths are
  never re-copied. Outside guest-mode a flagged COPY bails defensively.
- Outer guards evaluate on host; inner guards evaluate on guest.
- The remote block runs under the standard scope discipline
  (`push_scope`/`pop_scope`, `state.rs:316`): LET/ENV/WORKDIR/WORKSPACE
  unwind on exit. The ONLY things that cross are filesystem effects
  (tarball pack in, unpack out) and piped stdio already streamed.
  Host values enter as files or stdin bytes; results leave as files or
  stdout bytes. There is deliberately no mechanism for anything else.
- `ASYNC/AWAIT/CANCEL/TIMEOUT` inside body run guest-locally and join before
  return. Host-side wrapping works unchanged (session owned by host thread).
  Host cancel/timeout/partition closes stream and kills ssh child; guest
  discards partial state; results upload only on success.
- Chunk caps (64 KiB) on both sides; muxio has no backpressure, never slurp
  whole workspaces into one frame; tarball bytes ride as raw stream chunks,
  never base64 inside JSON.
- Stdio streaming via orthogonal `WITH_IO` block wrapping (no custom
  grammar, no parser change): `apply_io_defaults` (`parser.rs:940-954`)
  wraps any enclosed step kind, so a `REMOTE` step inside a
  `WITH_IO [stdin=$in, stdout=$out] { ... }` block automatically becomes
  `WithIo { bindings, cmd: RemoteBlock }`, flows through
  `dispatch_with_io` into `with_io`/`resolve_io_streams`, and arrives at
  `run_remote_block` with live `Arc<PipeInner>` backends on
  `StepCtx.out_pipe`/`stdin_pipe`. The single-line prefix form
  (`WITH_IO [...] REMOTE ...`) is NOT blessed: `WORKSPACE`
  stays a pure filesystem/execution-boundary directive and
  `WorkspaceTarget` stays closed (`Local/Snapshot/Cache/System`);
  `RemoteBlock` remains a distinct `StepKind`. Two supported shapes:
  outer host-side redirection (host pipes stream across the boundary)
  and guest-local `WITH_IO` on steps inside the block (guest pipes stay
  on the guest). There is no value payload at all (no `TaggedValue`, no
  `is_crossable` predicate: deleted with the variable design), so a `PIPE`
  *handle* can never be serialized anywhere; bytes move only through
  block-boundary redirection. Mechanics: guest stdout /
  stderr muxio chunks pump into the host `out_pipe` backend;
  a concurrent host drain thread reads the `stdin_pipe` backend into
  `exec` stdin chunks, and backend EOF sends the stream-close
  frame so guest stdin observes EOF. The stdin pump is mandatory and
  concurrent: without it stdin-wrapped remotes deadlock. `exec`
  is therefore bidirectional (stdin sub-stream host-to-guest alongside
  stdout/stderr guest-to-host).
- Interception covers THREE dispatch sites: the leaf path, the flow path,
  and `execute_single_step_with_generation` (the `with_io` re-execution
  path, `steps.rs:598`): without the third arm, a `WITH_IO`-wrapped
  remote misses interception. All three divert to
  `remote::run_remote_block`.
- Note: the method is `exec`, not `exec_script.v1`: no version suffixes
  exist anywhere in the protocol (see proto crate section).

## Protocol crate: `crates/oxdock-remote-proto` (new, shared)
- Deps only: `anyhow`, `serde`, `serde_json`, `sha2`, `muxio`, `tar`,
  `flate2`. No `oxdock-core`/`oxdock-parser`/`oxdock-fs` dependency; Miri-clean
  framing tests. Add `muxio`, `tar`, `flate2` to workspace (none in tree today).
- Methods (`rpc_method_id!` on STABLE names with no version suffix:
  `oxdock.remote.handshake`, `oxdock.remote.exec`, `oxdock.remote.close`).
  There is no manual protocol version anywhere. No `build.rs` either:
  the contract sources embed via `include_str!` (Cargo rebuilds on any
  edit natively, so no `rerun-if-changed` directives can go stale),
  canonicalize at first use through a `LazyLock<String>`
  (`PROTO_DIGEST`), hashed once per process. The workspace lint set bans
  raw `std::fs`/`std::path` outside sys crates, which a digest `build.rs`
  would need; the `include_str!` design sidesteps it entirely. Any
  contract edit changes the digest with zero manual steps; compatibility
  is decided by digest equality, never by comparing a human-maintained
  number. Fixture tests pin the canonicalization (comment/whitespace
  variants hash equal; any token change hashes different).
- Handshake (unary): client sends `PROTO_DIGEST`, oxdock version,
  sorted module NAMES, and module-table hash (sha2 over sorted module
  names plus function sets: language-surface identity). Names are
  runtime data from the registered modules, never cfg-flag chains, so
  downstream libraries surface automatically; mismatches name the
  symmetric difference. Server replies with its own tuple plus
  accept/reject. Reject unless digests are equal AND module hashes are
  equal; versions and names ride along for diagnostics and are logged on
  both sides. Any reject aborts
  before script bytes ship with both tuples and remediation (`rebuild
  and reinstall matching oxdock on the guest`). Sessions are
  single-block and short-lived, so no mid-session renegotiation: drift
  can only land   between blocks, where the next handshake catches it.
- `exec` (streaming, bidirectional: header carrying target, digest,
  and BOTH transfer declaration lists; script chunks; one FETCH stream
  (descriptor plus tar, entry names are guest-dest paths); stdin
  sub-stream host-to-guest; stdout/stderr chunks; one PUSH stream
  (descriptor plus tar, entry names are host-dest paths); terminal
  result JSON; result bytes out). `close` (unary, idempotent). Declared
  transfers fold into exec as framed sub-sections; method table stays at
  three entries, channel tags distinguish the streams.
- Tarball contract: gzip tar, 64 KiB chunks, sha256 in control JSON verified
  before unpack, forward-slash normalization, exclusion list
  (OS caches, cargo scratch, `.cache/workspace`) recorded in proto crate.
  Extraction is fail-closed through the active `PathResolver` on both
  sides (host unpack AND guest unpack of the input tarball): every entry
  resolves via `GuardedPath` under the active root; entries with `..`
  components, absolute paths, or symlinks resolving outside the root
  abort extraction immediately and terminate the session with an error
  (skip-and-continue would silently desync the manifests). Manifest-diff
  removals resolve through the same guard. Rationale split, documented in
  the proto crate docs and the user-facing fragment: the filesystem
  boundary is OxDock's domain (`oxdock-fs` containment, enforced
  identically host and guest); the execution boundary is the
  operator/OS domain (anyone needing isolated remote execution runs
  `oxdock --remote-serve` under a restricted UID, container, or
  ephemeral VM; OxDock never claims otherwise).
- Golden `serde_json` vectors, method-ID stability test, chunk-cap test.
  Frame decoder is bail-only on wire bytes (no panics, no `unwrap` on
  guest-supplied input; malformed frames kill the session with an error);
  fuzz target for the decoder is a recommended follow-up.

## Architecture: core primitive, NET-provided sessions
- Core (`oxdock-parser`, `oxdock-core`) owns the `REMOTE` keyword, its
  scoping, its `WITH_IO` mechanics, and the interception plumbing. Core
  never spawns ssh, never frames muxio, never packs tarballs.
- Everything remote lives behind the NET plugin
  (`crates/plugins/oxdock-net-plugin`): `--remote` inventory, the ssh
  stdio session, muxio framing (via `oxdock-remote-proto`), tarball
  pack/unpack, and the `--remote-serve` guest loop. Without the NET
  plugin compiled in, any `REMOTE` step bails:
  `REMOTE requires the NET plugin (build with --features net)`.
  Rationale: remote execution is networked execution; the `net` feature
  gate already governs `NET_*`, and remote sessions must never exist in
  a `--offline`-minded minimal build by accident.
- Seam: core defines a `RemoteRunner` trait in `exec/remote.rs`
  (`run_remote(RemoteRequest) -> RemoteResponse`) plus
  `Engine::set_remote_runner` (staged through `ExecIo`, zero signature
  churn). Registration is per target (`set_remote_runner_for_target`):
  one session per inventory entry, so concurrent blocks to different
  targets never share transport. `RemoteRequest` carries target, rendered
  script text, fetch entries as `(guest_rel, bytes)` pairs resolved by
  core under guard, push declarations as `(guest_rel, host_rel)` string
  pairs, live stdio backends, and the host cancellation token.
  `RemoteResponse` carries stdout/stderr bytes (appended by core to
  whatever backends already received), push entries as `(host_rel,
  bytes)` plus push symlinks, and nothing else: no full workspace, no
  deletion manifests. The NET plugin registers its session factory at
  CLI startup (`cli_host_modules_with` time). Unbound targets bail with
  the exact `--remote` flag to add. Mock runners implement the same
  trait in tests with zero ssh.
- `oxdock-remote-proto` stays dependency-light (anyhow, serde,
  serde_json, sha2, muxio, tar, flate2) and is consumed by the NET
  plugin, never by core.

## Host side (NET plugin)
- `oxdock-net-plugin/src/remote/` (new module): `flags.rs`
  (`RemoteFlags`, pure parsers mirroring `EndpointFlags` style),
  `inventory.rs` (`RemoteInventory`, post-parse target validation),
  `session.rs` (`SshStdioSession` implementing core `RemoteRunner`).
  Single repeatable flag (no flag trio):
  `oxdock --remote <target>="<command string>"`, e.g.
  `oxdock --remote macos_target="ssh -i /keys/ci_ed25519 user@mac-mini /opt/oxdock/bin/oxdock" build_script.ox`.
  (`run` is a DSL keyword, not a CLI subcommand: the CLI takes a
  positional script path or `--script`.)
  The command string is tokenized ONCE at host startup with POSIX
  shell-word rules (`shell-words` crate): naive whitespace splitting
  corrupts quoted SSH options (e.g. `-o "ProxyCommand=ssh -W %h:%p
  jump"`). Tokenization failure (unclosed quotes) or an empty vector
  fails CLI startup fast. `session.rs` appends `--remote-serve` as the
  final element and passes the vector directly to
  `oxdock-process::CommandBuilder::new(&argv[0]).args(&argv[1..])`
  (direct `execvp`/`CreateProcessW`, never `sh -c`). Duplicate target
  bails. DSL scripts keep target-only identifiers; all transport detail
  stays in the CLI invocation. New workspace dep: `shell-words`.
- Startup: read script, build endpoint registry, parse to AST, scan AST
  for `StepKind::RemoteBlock` targets, validate against
  `RemoteInventory`, fail fast before execution
  (`unknown remote target "win-arm" (declared: [...])`); log every
  target-to-endpoint resolution to stderr; no remote blocks means no ssh
  ever. Target collection is post-parse by construction (targets live in
  AST nodes).
- Session: lazy connect on first block entry, one transport stdio
  process per block entry via `oxdock-process` (`CommandBuilder` gains
  `stdout_piped`/`stderr_piped` plus piped spawn returning halves).
  The transport is ANY command yielding a bidirectional stdio pipe to an
  `oxdock --remote-serve` guest, not just ssh: local subprocess
  (`--remote t="oxdock"`), `docker exec -i <ctr> oxdock`, `kubectl exec
  -i <pod> -- oxdock`, `wsl oxdock`. Validity constraints (documented):
  stdio transparency (no byte transformation; binary-safe), no TTY
  allocation (`ssh -t` / `docker exec -t` corrupt muxio framing via
  `\n` to `\r\n` translation), clean EOF propagation (closing host
  stdin ends the guest session). muxio over child pipes with
  reader/writer pump threads (existing `pump_stream` precedent in the
  same crate). Scoped teardown via Drop. No pooling, no shared remote
  workspace v1; concurrent blocks are separate sessions.
- Interception (core): `StepKind::RemoteBlock` diverts in
  `crates/oxdock-core/src/exec/steps.rs` (leaf path, flow path, AND
  `execute_single_step_with_generation`, which is the `with_io`
  re-execution path a `WITH_IO`-wrapped remote takes) to
  `remote::run_remote_block` (new `exec/remote.rs`: render header plus
  body text, resolve `COPY --from-host` declarations to bytes under
  guard, stream stdio pipes, apply push entries plus push symlinks under
  guard). The block runs inside the normal scope discipline (`push_scope`
  before, `pop_scope` after, or equivalently `execute_scoped_steps`):
  LET/ENV/WORKDIR/WORKSPACE unwind; only declared push effects persist,
  exactly like local blocks. `dispatch_remote` in `handlers.rs` wired
  through `define_pipeline!`. `StepCtx`/`Engine` carry the optional
  runner; absent means the NET-plugin bail above.
  Never touches `switch_to_*`.

## Guest side (NET plugin, `--remote-serve` hidden flag)
- Hidden `--remote-serve` in `oxdock-cli`, available only when the NET
  feature is compiled in (bails otherwise, same as `NET_*` without the
  feature). Rejects combination with `--script`, `--shell`, `--listen`,
  `-p`, positional script; bails on TTY stdio.
- Loop: handshake, then per `exec` request create a FRESH EMPTY
  `GuardedPath::tempdir` staging workspace (nothing ships by default),
  unpack the FETCH tarball into it under guard, build guest `Engine`
  with `cli_host_modules`/`cli_host_types` plus guest-mode set (flagged
  `COPY` steps acknowledge as no-ops; transfers already fulfilled),
  parse text with own module table, execute, stream chunks, pack declared
  PUSH paths (missing sources fail the exec), send terminal result plus
  push tar. Guest scope unwinds the same way; no variable outputs are
  captured. Temp workspace dropped after response; no persistence v1.
- stdout strictly frames; diagnostics to stderr only; byte-oriented IO with
  `\r\n`/NUL tests. Missing/stale guest binary surfaces as handshake
  failure fixed operator-side.

## File transfer (explicit declarations only, never bulk sync)
- Entry: host walks ONLY `COPY --from-host` declared paths (each a file
  or recursive dir) under the host active root (`cx.state.fs.root()`),
  never the whole tree. Missing sources fail fast before any session
  byte ships. Entries ride one `exec`-method FETCH stream as
  length-prefixed descriptor plus tar bytes; entry names are the
  guest-destination relative paths. Guest verifies sha256, unpacks into
  the empty staging dir under guard.
- Guest-side root matrix is unchanged (SNAPSHOT staging, LOCAL process
  dir, CACHE user cache, SYSTEM unconfined) but the staging dir starts
  empty and only fetched entries exist. Guest writes anywhere with
  normal local semantics.
- Exit: guest tars ONLY `COPY --to-host` declared paths from staging
  (missing sources fail the exec loudly), streams one PUSH stream;
  host verifies sha256, unpacks entries (named as host-destination
  relative paths) into its active root under guard, materializing
  symlinks only when targets resolve inside the root. No manifest diff,
  no deletion propagation: guest deletions affect nothing on the host.
  `pop_scope` restores the prior root *selection* while pushed file
  effects persist, exactly like local blocks.
- Bulk sync and fingerprint caching are NOT planned in any form:
  explicit declarations are the mechanism, full stop. The earlier
  on-demand FETCH/PUSH round-trip variant (guest-issued requests
  mid-execution) is rejected with it: hoisted proactive streams keep the
  protocol request/response-free and block-granular.

## Step order (green at each step)
1. Parser: `RemoteBlock` variant (target, vars, env, body), lowering
   (static target, entry validation `$var` vs `env:NAME`, self-containment,
   remote-in-remote, `INHERIT_ENV` rejections), `COPY --from-host` /
   `--to-host` flags (mutually exclusive, valid only inside `REMOTE`
   via `LowerCtx` remote-depth, `Display` round-trip), Display,
   pest/parser block path, mock lowering, round-trip tests. Engine gets
   a temporary exhaustive arm bailing `REMOTE requires the NET plugin
   (not yet wired)`.
2. Core `exec/remote.rs` with `RemoteRunner` trait, scoped execution,
   header-list resolution (render LET/ENV, prepend),
