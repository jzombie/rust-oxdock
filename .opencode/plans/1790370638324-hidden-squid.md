# Plan: Remote Execution Context (issue #158)

## Goal
`REMOTE <target> { ... }` blocks execute sealed from outer scope on a
remote guest running its own OxDock binary. Guest self-provisions (host
never builds or ships guest binaries). Transport is the system `ssh`
binary over stdio, framed with `muxio` (crates.io, v0.16 alpha line).
Core owns the block primitive; everything remote lives behind the NET
plugin. Toolchain-plugin work from #179 is shelved and out of scope.

## Locked decisions (from owner)
- Closed scope, in the keyword: no variables cross in either direction.
  `WITH_IO` pipe bindings plus synced files are the sole communication.
- Target-only in scripts. No transport vocabulary in the DSL. Host
  inventory binds targets at startup, fail-fast, with resolution logging.
  Same posture as the `EndpointRegistry` built from
  `--listen`/`-p`/`--offline`.
- OS-facilitated SSH only, never russh. OxDock owns framing, not auth.
- Per-command RPC is rejected. Protocol is block-granular: new DSL commands
  work remotely automatically with zero protocol changes.
- Text is the shippable unit (`Display` round-trip already guaranteed).
- Host wins on partition. Stream close equals cancel.
- Core primitive, NET-provided sessions: without the NET plugin, `REMOTE`
  bails with an actionable error.

## DSL shape: `REMOTE` with header binding list
- New `StepKind::RemoteBlock { target: String, vars: Vec<String>,
  env: Vec<String>, body: Vec<Step> }` in
  `crates/oxdock-parser/src/commands.rs`. `WORKSPACE` is untouched and
  `WorkspaceTarget` stays closed: the `WORKSPACE` prefix promised switch
  semantics this construct cannot honor. `REMOTE` states the act (run this
  block on that target); the header list states the data dependencies.
  No wrapper keywords, no nesting, no prefixes, no in-body declarations.
- Syntax:
  ```oxdock
  WORKSPACE LOCAL
  ECHO "do something on host"
  WITH_IO [stdout=$out] {
      REMOTE prod [$version, env:DEPLOY_ENV] {
          RUN ./deploy.sh $version
      }
  }
  # Host scope restored; READ files or $out for results.
  ```
  `REMOTE <target> [<bindings>] { ... }` takes a static-literal target,
  an optional bracket list, and a mandatory braced body. List entries are
  `$var` (outer `LET` variable, same-name injection) or `env:NAME`
  (outer env key); anything else bails at lower time, as do dynamic
  names. Empty and omitted lists are identical (fully sealed).
  Same-name injection only (renaming deferred, not v1). Canonical
  Display renders the header on one line and the body indented.
- Closed scope: nothing crosses except header-listed names, `WITH_IO`
  bytes, and synced files. The block otherwise sees only guest-local
  environment.
- Injection mechanics (no value protocol): at interception the host
  resolves each listed name against its live scope, renders a `LET` /
  `ENV` declaration line, and prepends the lines to the shipped text, so
  the guest parses ordinary steps. Renderable set (tight v1): `STRING`,
  `INT`, `FLOAT`, `BOOL`, `DURATION`, and `LIST`/`MAP` composed solely of
  those, reusing the host declaration kind
  (`LET $version: STRING = "1.2.3"`). Rendering uses canonical DSL
  literal escaping, the exact inverse of runtime `expand_string`
  (`args.rs:893-897`): `\` to `\\`, `"` to `\"`, newline to `\n`, CR to
  `\r`, tab to `\t`, and `{{` to `\{{` (unescaped braces would
  interpolate guest-side). A dedicated `render_dsl_literal` helper owns
  this table (not the `quote_arg`/`quote_msg` Display helpers, which do
  not cover control characters); round-trip property tests assert
  parse(render(v)) == v, including hostile strings (quotes, backslashes,
  newlines, `{{ $x }}`, instruction-boundary `;`/`}`). Unknown names bail
  (`REMOTE 'prod' uses unknown variable $foo`); anything else (`PIPE`,
  `HANDLE`, `SEMAPHORE`, `PERMIT`, `PATH`, host opaque types) bails
  naming the variable (`cannot pass $p: PIPE into REMOTE 'prod' (pass
  bytes via WITH_IO, files via the workspace)`). A body `LET` colliding
  with a passed name hits the normal guest redeclaration error (loud,
  correct).
- `WITH_IO` remains the sole byte channel, orthogonally (parse-time
  expansion wraps the `RemoteBlock` step with zero parser changes,
  `parser.rs:940-954`); the single-line prefix form is not blessed.
- Self-containment is AST-symbol only (never consults the runtime
  module table): lowering collects `DefineFunc` names declared outside
  the `RemoteBlock` vs inside it, walks the body for call nodes and
  call expressions, and bails only when a call matches an *outer
  user-defined* symbol and no inner one:
  `REMOTE 'prod' calls outer function 'build' (functions must be defined
  inside the block)`. Native `StepKind`s (`Echo`, `Read`, `Write`, ...),
  builtins, and `IMPORT`ed module functions pass untouched by
  construction: they are distinct variants/symbols, not `DefineFunc`
  nodes, so the check cannot misfire on them.
- The target is a static literal naming an inventory entry bound with
  `--remote`. Deferred or computed selection is not expressible (no
  `$var`, no `{{ }}`): the same script targets a different machine by
  rebinding inventory, never by editing. Unresolved target is a startup
  error after parse, before execution.
- Lowering validation: `^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$`; reserved words
  (`SNAPSHOT`, `LOCAL`, `CACHE`, `SYSTEM`, `REMOTE`) rejected.
- Guest-local semantics inside body: `WORKSPACE` selection, `COPY`, `RUN`
  resolve against guest roots and guest module table.
  Host `-p`/`--listen`/`--offline` never cross. `--offline` does not
  disable remote execution (outbound ssh stdio, no listening socket).
- `parse_script(Display) == original` must hold; add round-trip tests.
  Extend `test_lower_mock::lower` in lockstep.

## Boundary semantics
- Host resolves header-listed names against its live scope, renders
  `LET`/`ENV` lines, prepends them to `body` text (`step.to_string()`),
  ships text plus snapshot reference in one `exec_script` stream. NO
  value payload. Guest parses with its own `parse_script_with_modules`
  and runs the full engine (`run_steps_with_lazy_snapshot_and_modules`).
  No per-command dispatch.
- Outer guards evaluate on host; inner guards evaluate on guest.
- The remote block runs under the standard scope discipline
  (`push_scope`/`pop_scope`, `state.rs:316`): LET/ENV/WORKDIR/WORKSPACE
  unwind on exit. The ONLY things that cross are filesystem effects
  (tarball pack in, unpack out) and piped stdio already streamed.
  Host values enter as files or stdin bytes; results leave as files or
  stdout bytes. There is deliberately no mechanism for anything else.
- `ASYNC/AWAIT/CANCEL/TIMEOUT` inside body run guest-locally and join before
  return. Host-side wrapping works unchanged (session owned by host thread).
  Host cancel/timeout/partition closes stream and kills ssh child; guest
  discards partial state; results upload only on success.
- Chunk caps (64 KiB) on both sides; muxio has no backpressure, never slurp
  whole workspaces into one frame; tarball bytes ride as raw stream chunks,
  never base64 inside JSON.
- Stdio streaming via orthogonal `WITH_IO` block wrapping (no custom
  grammar, no parser change): `apply_io_defaults` (`parser.rs:940-954`)
  wraps any enclosed step kind, so a `REMOTE` step inside a
  `WITH_IO [stdin=$in, stdout=$out] { ... }` block automatically becomes
  `WithIo { bindings, cmd: RemoteBlock }`, flows through
  `dispatch_with_io` into `with_io`/`resolve_io_streams`, and arrives at
  `run_remote_block` with live `Arc<PipeInner>` backends on
  `StepCtx.out_pipe`/`stdin_pipe`. The single-line prefix form
  (`WITH_IO [...] REMOTE ...`) is NOT blessed: `WORKSPACE`
  stays a pure filesystem/execution-boundary directive and
  `WorkspaceTarget` stays closed (`Local/Snapshot/Cache/System`);
  `RemoteBlock` remains a distinct `StepKind`. Two supported shapes:
  outer host-side redirection (host pipes stream across the boundary)
  and guest-local `WITH_IO` on steps inside the block (guest pipes stay
  on the guest). There is no value payload at all (no `TaggedValue`, no
  `is_crossable` predicate: deleted with the variable design), so a `PIPE`
  *handle* can never be serialized anywhere; bytes move only through
  block-boundary redirection. Mechanics: guest stdout /
  stderr muxio chunks pump into the host `out_pipe` backend;
  a concurrent host drain thread reads the `stdin_pipe` backend into
  `exec_script` stdin chunks, and backend EOF sends the stream-close
  frame so guest stdin observes EOF. The stdin pump is mandatory and
  concurrent: without it stdin-wrapped remotes deadlock. `exec_script.v1`
  is therefore bidirectional (stdin sub-stream host-to-guest alongside
  stdout/stderr guest-to-host).
- Interception covers THREE dispatch sites: the leaf path, the flow path,
  and `execute_single_step_with_generation` (the `with_io` re-execution
  path, `steps.rs:598`): without the third arm, a `WITH_IO`-wrapped
  remote misses interception. All three divert to
  `remote::run_remote_block`.

## Protocol crate: `crates/oxdock-remote-proto` (new, shared)
- Deps only: `anyhow`, `serde`, `serde_json`, `sha2`, `muxio`, `tar`,
  `flate2`. No `oxdock-core`/`oxdock-parser`/`oxdock-fs` dependency; Miri-clean
  framing tests. Add `muxio`, `tar`, `flate2` to workspace (none in tree today).
- Methods (`rpc_method_id!`): `oxdock.remote.handshake.v1` (unary.
  Client sends protocol version (proto crate semver), oxdock version,
  feature-flag set, and module-table hash (sha2 over sorted module names
  plus function sets, so the gate tracks language surface, not release
  numbers). Server replies with its own tuple plus accept/reject. Reject
  unless protocol majors match AND module-table hashes are equal; oxdock
  versions and feature sets ride along for diagnostics, not gating, so a
  patch release with an identical language surface interops. Any reject
  aborts before script bytes ship with both tuples and remediation
  (`install matching oxdock on the guest`). Sessions are single-block
  and short-lived, so no mid-session renegotiation: drift can only land
  between blocks, where the next handshake catches it.), `oxdock.remote.exec_script.v1`
  (streaming: header carrying only target, protocol version, and
  capabilities; script chunks and snapshot bytes in; stdin sub-stream
  host-to-guest; stdout/stderr chunks, terminal result JSON, result bytes
  out), `oxdock.remote.close.v1`
  (unary, idempotent). File sync folds into exec as framed sub-sections;
  method table stays at three entries.
- Tarball contract: gzip tar, 64 KiB chunks, sha256 in control JSON verified
  before unpack, forward-slash normalization, guarded unpack, exclusion list
  (OS caches, cargo scratch, `.cache/workspace`) recorded in proto crate.
- Golden `serde_json` vectors, method-ID stability test, chunk-cap test.

## Architecture: core primitive, NET-provided sessions
- Core (`oxdock-parser`, `oxdock-core`) owns the `REMOTE` keyword, its
  scoping, its `WITH_IO` mechanics, and the interception plumbing. Core
  never spawns ssh, never frames muxio, never packs tarballs.
- Everything remote lives behind the NET plugin
  (`crates/plugins/oxdock-net-plugin`): `--remote` inventory, the ssh
  stdio session, muxio framing (via `oxdock-remote-proto`), tarball
  pack/unpack, and the `--remote-serve` guest loop. Without the NET
  plugin compiled in, any `REMOTE` step bails:
  `REMOTE requires the NET plugin (build with --features net)`.
  Rationale: remote execution is networked execution; the `net` feature
  gate already governs `NET_*`, and remote sessions must never exist in
  a `--offline`-minded minimal build by accident.
- Seam: core defines a `RemoteRunner` trait in `exec/remote.rs`
  (`run_remote(target, body_text, snapshot_in, io_pipes) -> RemoteOutcome`)
  plus `Engine::set_remote_runner`. The NET plugin registers its session
  factory at CLI startup (`cli_host_modules_with` time). No runner means
  the actionable bail above. Mock runners implement the same trait in
  tests with zero ssh.
- `oxdock-remote-proto` stays dependency-light (anyhow, serde,
  serde_json, sha2, muxio, tar, flate2) and is consumed by the NET
  plugin, never by core.

## Host side (NET plugin)
- `oxdock-net-plugin/src/remote/` (new module): `flags.rs`
  (`RemoteFlags`, pure parsers mirroring `EndpointFlags` style),
  `inventory.rs` (`RemoteInventory`, post-parse target validation),
  `session.rs` (`SshStdioSession` implementing core `RemoteRunner`).
  Flags: `--remote <target>=<ssh-destination>` (repeatable),
  `--remote-oxdock <target>=<guest-binary-path>` (default `oxdock` on
  guest PATH), `--remote-ssh-opt [-]<target>=<option>` (global or
  per-target). Duplicate target bails. `=` form because destinations may
  contain colons.
- Startup: read script, build endpoint registry, parse to AST, scan AST
  for `StepKind::RemoteBlock` targets, validate against
  `RemoteInventory`, fail fast before execution
  (`unknown remote target "win-arm" (declared: [...])`); log every
  target-to-endpoint resolution to stderr; no remote blocks means no ssh
  ever. Target collection is post-parse by construction (targets live in
  AST nodes).
- Session: lazy connect on first block entry, one `ssh [opts] <dest>
  <guest-bin> --remote-serve` stdio process per block entry via
  `oxdock-process` (`CommandBuilder` gains `stdout_piped`/`stderr_piped` plus
  piped spawn returning halves). muxio over child pipes with reader/writer
  pump threads (existing `pump_stream` precedent in the same crate).
  Scoped teardown via Drop. No pooling, no shared remote workspace v1;
  concurrent blocks are separate sessions.
- Interception (core): `StepKind::RemoteBlock` diverts in
  `crates/oxdock-core/src/exec/steps.rs` (leaf path, flow path, AND
  `execute_single_step_with_generation`, which is the `with_io`
  re-execution path a `WITH_IO`-wrapped remote takes) to
  `remote::run_remote_block` (new `exec/remote.rs`: render body text,
  resolve runner, stream stdio pipes, unpack result tarball). The block
  runs inside the normal scope discipline (`push_scope` before,
  `pop_scope` after, or equivalently `execute_scoped_steps`): LET/ENV/
  WORKDIR/WORKSPACE unwind; only unpacked file effects persist, exactly
  like local blocks. `dispatch_remote` in `handlers.rs` wired through
  `define_pipeline!`. `StepCtx`/`Engine` carry the optional runner;
  absent means the NET-plugin bail above.
  Never touches `switch_to_*`.

## Guest side (NET plugin, `--remote-serve` hidden flag)
- Hidden `--remote-serve` in `oxdock-cli`, available only when the NET
  feature is compiled in (bails otherwise, same as `NET_*` without the
  feature). Rejects combination with `--script`, `--shell`, `--listen`,
  `-p`, positional script; bails on TTY stdio.
- Loop: handshake, then per `exec_script` request create fresh
  `GuardedPath::tempdir` workspace, unpack snapshot, build guest `Engine`
  with `cli_host_modules`/`cli_host_types`, parse text with own module
  table, execute, stream chunks, send terminal result plus result tar.
  Guest scope unwinds the same way; no variable outputs are captured.
  Temp workspace dropped after response; no persistence v1.
- stdout strictly frames; diagnostics to stderr only; byte-oriented IO with
  `\r\n`/NUL tests. Missing/stale guest binary surfaces as handshake
  failure fixed operator-side.

## File sync (v1: unconditional, full, against the ACTIVE root)
- Entry: pack the host's currently active workspace root
  (`cx.state.fs.root()`), never a hardcoded SNAPSHOT path. Under
  `WORKSPACE LOCAL` the guest receives the local tree; under SNAPSHOT the
  snapshot view (materializing it if still lazy). Packing a hardcoded
  snapshot root while LOCAL is selected would ship an empty tree and dump
  results into the wrong directory: silent data loss.
- Guest-side root matrix (enforced in `oxdock-remote-proto` docs and guest
  serve loop): guest `SNAPSHOT` is the ephemeral staging dir holding the
  shipped tree; guest `LOCAL` is the `oxdock --remote-serve` process
  working directory on the remote machine; guest `CACHE` is the remote
  user's persistent OS cache; guest `SYSTEM` is the unconfined remote
  filesystem. The guest may switch among these inside the block with
  normal local semantics.
- Exit harvests STRICTLY the guest staging dir (`SNAPSHOT`), irrespective
  of the guest's active selection at block end. Files the guest wrote
  under guest `LOCAL`/`CACHE`/`SYSTEM` stay on the guest and are never
  packed. Harvesting the active root or wider would corrupt the host
  workspace with remote OS files. Host verifies sha256, unpacks into its
  own active root via guarded writes before scope exit, then propagates
  deletions by manifest diffing: `deleted = input_tar_paths -
  return_tar_paths` (relative-path `HashSet`s recorded at pack/unpack
  time), executing guarded `remove_file` (`oxdock-fs`
  `workspace_fs/io.rs`) on the host's active resolver for every missing
  path. Plain tarball extraction cannot delete, so the diff is mandatory,
  not an optimization. `pop_scope` restores the prior
  root *selection* while unpacked file effects persist, exactly like local
  blocks. No selection is ever switched by the remote machinery.
- Fingerprint caching deferred behind a protocol version bump.

## Tests (mock-first, no ssh except native-only)
- `oxdock-remote-proto` tests: golden JSON, method IDs, chunk caps,
  memory-transport framing and cancel. Run under Miri.
- Parser tests: round-trips (canonical header list, empty list, guarded
  inners, nested `IF`/`TIMEOUT`, target edges), entry validation
  (bare names, bad prefixes, dynamic names rejected), `remote-in-remote`,
  `INHERIT_ENV`, inline-form (unbraced) rejection, outer-`FUNC`-call
  rejections (direct and transitive through an inner `FUNC`; builtins
  and `IMPORT`ed calls pass).
- `oxdock-core` `remote_mock.rs`: mock `RemoteRunner` with in-process
  stdio pipes (no muxio, no ssh). Sealed-scope proof (`LET`/`ENV` inside
  invisible after exit; file WRITE inside visible via READ outside),
  header-list injection (scalars plus nested LIST/MAP render
  and execute; hostile strings with quotes, backslashes, newlines, and
  `{{ }}` round-trip byte-identical; unknown name bails; `PIPE` entry
  bails naming the var; malformed entry bails; body collision hits guest
  redeclaration error), guest deletion propagation (guest deletes a
  shipped file, host file is removed after unpack),
  `WITH_IO`-wrapped remote (stdin bytes in, echo, stdout bytes out, EOF
  propagation, no deadlock), missing-runner bail naming the NET plugin.
  Runs under Miri.
- NET plugin `remote_mock.rs`: in-process muxio over memory pipes.
  Handshake ok/mismatch, empty body, ECHO round-trip, active-root sync
  (LOCAL selection round-trips to the local tree, SNAPSHOT to the
  snapshot view), guest root-switch exclusion (guest writes under guest
  LOCAL/CACHE stay on the guest, absent from the return tarball even when
  guest ends with a non-SNAPSHOT selection), full `WITH_IO` stdio loop
  through muxio framing, chunk interleaving, tar sha mismatch, close
  idempotence, symlink parity Unix plus Windows. Runs under Miri.
- CLI tests: flag parsing, inventory errors, offline interaction, hidden
  flag combination rejections. Real-ssh tests native-only with
  `#[cfg_attr(miri, ignore = "...")]` reasons.
- Docs: `remote:mock` fence metadata hook for `docs_conformance` so
  remote fences execute through the mock runner; `#` comment per stanza;
  `IMPORT` at top.
- Style: `oxdock!` plus `indoc` scripts, no `\n` joins; no em dashes in
  prose; localized `#[allow]` only; guarded paths via `oxdock-fs`;
  processes via `oxdock-process`; no raw `std::process::Command`.

## Step order (green at each step)
1. Parser: `RemoteBlock` variant (target, vars, env, body), lowering
   (static target, entry validation `$var` vs `env:NAME`, self-containment,
   remote-in-remote, `INHERIT_ENV` rejections), Display, pest/parser block
   path, mock lowering, round-trip tests. Engine gets a temporary
   exhaustive arm bailing `REMOTE requires the NET plugin (not yet wired)`.
2. Core `exec/remote.rs` with `RemoteRunner` trait, scoped execution,
   header-list resolution (render LET/ENV, prepend),
   `WITH_IO` pipe passthrough, mock-runner tests. No runner
   (no NET) bails cleanly with the actionable message.
3. `oxdock-remote-proto` crate alone with types, method IDs, tar helpers,
   tests. No dependents yet.
4. NET plugin `remote/` module: flags, inventory build, post-parse target
   validation, resolution logging. No ssh spawn yet.
5. `oxdock-process` piped stdio plus `session.rs` ssh session implementing
   `RemoteRunner`, native-only tests.
6. Guest `--remote-serve` loop (NET-gated) with handshake gating and
   per-exec temp workspace.
7. File sync end to end through mock first, then real ssh native-only.
8. Docs fragments, regenerated READMEs via `cargo run -p docs-gen`,
   logic-test fixtures, conformance hook. Final full
   `cargo test --workspace --tests` plus docs-gen regeneration.
