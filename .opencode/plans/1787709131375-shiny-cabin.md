## F1 — Template spacing math (`macro_input.rs`) — BOTH sides were wrong

Trailing side (as directed): `{{X}}` puts exactly two braces between the last inner char and the outer span end (distance 2); a single space makes it 3. Change threshold to `> end.column + 2`.

Leading side (same class, reviewer-adjacent): seeding `last_span_end = span.start()` makes `span_gap_requires_space` fire even for unspaced `{{X}}` (inner token col > outer-open col always). Seed instead at the SECOND brace:
```rust
let mut inner_span_end = Some(LineColumn {
    line: span.start().line,
    column: span.start().column + 1,
});
```
Add regression tests pinning BOTH variants byte-for-byte: `WRITE f.txt Built with {{ env:P }}` (spaced) AND `WRITE f.txt Built with {{env:P}}` (unspaced) — each must render identically and parse to the same AST interior.

## F2 — `TeeWriter` sink isolation (`oxdock-core/src/exec/io.rs`)

Adopt directed `flush()` (match; poisoned lock → `io::Error::other`, stdout flush ONLY when inner is None). Same defect class exists in `write()`: `Some`+poisoned currently silently skips sink writes while still returning Ok — make `write()` propagate the lock error symmetrically.

## F3 — Platform-agnostic repo-root anchoring (both test files)

Windows `CARGO_MANIFEST_DIR` uses backslashes; forward-slash `strip_suffix` fails there. Deviation from Directive 3's `std::path::Path::ancestors(...)`: `Path`/`PathBuf` are clippy-disallowed OUTSIDE `crates/sys/*`, and AGENTS.md forbids local `#[allow]`s in non-sys crates. then unchanged `strip_suffix("/oxdock-cli")` / `strip_suffix("crates/oxdock-logic-tests")`. Forward-slash roots are valid on Windows for all downstream `GuardedPath`/fs use.

## Part 1 — `oxdock-parser`: new `src/markdown.rs`

Public API:
```rust
pub struct BlockMetadata {
    pub env: Vec<(String, String)>,
    pub stdin: Option<String>,
    pub unified_roots: bool,
    pub expect_error: Option<String>,
}
pub struct FencedBlock { pub line_no: usize, pub info_string: String, pub metadata: BlockMetadata, pub body: String }
pub fn extract_fenced_blocks(markdown: &str, lang: &str) -> Result<Vec<FencedBlock>>
```
- Fence scan: ≥3-backtick runs (indent ≤3 spaces), close requires tick-run ≥ opener + empty rest; shorter/nested runs = body content; unclosed fence at EOF = error; blocks filtered by first info-token == `lang`
- Metadata: **character-by-character scanner** over tokens after `lang` — space-delimited items, with text enclosed in double quotes preserved verbatim across spaces (e.g. `expect_error="EXIT requested with code 42"`). Raw `split_whitespace()` is prohibited (it fragments quoted values). Keys: `env` (repeatable `K=V`), `stdin`, `roots` (only `unified`), `expect_error`; **unknown key = hard error** (typo-proofing)
- Export from lib.rs. Unit tests in-module: ticks/indent/closing rules, CRLF bodies, line numbers, lang filtering, metadata scanner (quoted values containing spaces/multiple words, repeated `env:` pairs, unknown-key errors, unterminated quote = error)
- One-liner mention in `crates/oxdock-parser/README.md` architecture section

## Part 2 — Language: 4 new commands

Grammar (`dsl.pest`, ordered before similar prefixes where needed). `ASSERT_FILE` uses two explicit alternatives so the `--hash` digest can never be captured into the path slot (positional inversion), and a missing digest after `--hash` is a parse error rather than silent skip:
```pest
assert_file_command = { assert_file_hash_command | assert_file_content_command }
assert_file_hash_command = ${ "ASSERT_FILE" ~ sep ~ "--hash" ~ sep ~ hash_digest ~ sep ~ argument }
assert_file_content_command = ${ "ASSERT_FILE" ~ sep ~ !hash_flag ~ argument ~ (sep ~ message)? }
assert_dir_command  = ${ "ASSERT_DIR" ~ sep ~ argument }
assert_absent_command = ${ "ASSERT_ABSENT" ~ sep ~ argument }
assert_stdout_command = ${ "ASSERT_STDOUT" ~ sep ~ message }
hash_flag = { "--hash" }
hash_digest = @{ ASCII_HEX_DIGIT{64} }
```
The `!hash_flag` lookahead on the content form guarantees any input beginning with `--hash` matches ONLY the hash branch — a malformed digest (not 64 hex chars) fails loudly at `hash_digest` instead of silently re-parsing `--hash` as the path. Alternation order (hash first) mirrors the existing `run_bg_command`-before-`run_command` precedent. Parser unit tests must pin both directions: `ASSERT_FILE --hash <sha> <path>` parses with digest/path in the correct slots, and `ASSERT_FILE --hash <bad-digest> <path>` is a parse error (no content-form fallback).
Semantics (cwd-relative like `READ`/`WRITE`; templates expand; guards/blocks apply normally):
- `ASSERT_FILE [--hash <sha256>] <path> [<expected>]` — file exists; exact byte match vs expanded contents, or `hash_path` digest equality with `--hash`
- `ASSERT_DIR <path>` / `ASSERT_ABSENT <path>`
- `ASSERT_STDOUT <substring>` — everything the script emitted to its stdout sink (interpreter AND streamed child output), see tee below
