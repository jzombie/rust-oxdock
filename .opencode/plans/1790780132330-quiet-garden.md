# Plan: Make docs-gen a Truly Agnostic Templating Engine

## Context

`docs-gen` today is a native OxDock pipeline that renders every `README.md` from templates. Core mechanics are already generic (glob fragments by group, stem rule, master template ordering, strict `{{ }}` expansion via `StreamingExpand`). OxDock coupling is layered on top: DSL orchestration in `lib.rs`, Cargo manifest sync, registry generated fragments, hardcoded var names (`docs_global`, `docs_ctx`, `$files`), `CRATE_VERSION`, `target/oxdock-docs` staging, static plugin links.

User direction:
- Yes to rename. Do not settle now. Candidates like `templex`, `stencil`, `forg` are placeholders. Add explicit research task.
- OxDock coupling becomes optional plugins, not removal without path.
- Priority use cases: resumes and documents, any README or docs, just engine API. Source code output must stay possible but is not the first driver.
- Initial spec includes one code generation element: integrating https://github.com/jzombie/rust-oxdock/issues/170 (render MAP as Markdown table) as an OxDock-callable module with the template engine piggybacking on it. Formatter scope stays per placeholder, not per document, so Markdown inside Rust comments and similar embeds keep working. JSON-LD is explicitly not a built in formatter. It was only an example. JSON-LD output is a plain templated file (single entry template plus values) rendered through normal expansion or a function call, not engine generated from scratch.

## Proposal Summary

Two layer topology, DSL-first per user (revised: no separate
`template-core` crate; `docs-gen` is the engine, whatever it gets
renamed to later):

1. `crates/docs-gen` (rename TBD by research): the generic file set
   renderer. Written mostly in OxDock DSL itself: DSL script stages
   (`BUILD_MANIFEST`, `RENDER_TARGET`, duplicate guards) plus a small
   `TEMPLATE` HostModule of pure helpers (`FILE_STEM`, `HAS_KEY`,
   `MAP_SET`, `TO_JSON`, `EXPAND_FRAGMENT`). Agnostic means generic
   inputs and outputs (any `values.json`, fragments, targets:
   READMEs, resumes, `llms.txt`, source files), not dependency
   purity. Depending on OxDock is expected.
2. `crates/plugins/oxdock-markdown-plugin` plus a future
   `oxdock-docs-provider`: capability and domain specifics. The
   plugin ships the `MARKDOWN` HostModule (`MAP_TO_MD_TABLE`) over a
   pure `markdown` module (single source for table rendering and
   cell escaping, shared with `docs-gen` reference renderers).
   The provider will hold OxDock registry content (command index
   and body, function reference, plugin refs, Cargo sync).

Rule: sequencing, globs, reads, writes, loops, and error exits stay in DSL. Rust exists only where the DSL has no primitives (pure string, map, table, JSON transforms plus narrow readers).

Selective pull from B2A context (only what the templating engine owns):
- Dual target output: the engine must support emitting human `README.md` plus agent `llms.txt` and `llms-full.txt` from the same values and fragments in one run. This is just multi target config, no special casing.
- JSON-LD as template, not formatter: Schema.org `maintainer` and `publisher` links (jzombie as author, zenOSmosis as publisher) are covered by a plain JSON-LD template example, not engine code. A generic `[json]` value formatter may exist for embedding values, but no `[json-ld]` formatter ships in v1.
- Crate isolation: keep strict boundaries between workspace crates (`crates/sys/*`, `crates/oxdock-core`, `crates/plugins/*`), but `docs-gen` depending on OxDock is expected. MCP server gating is explicitly out of scope here.

## Step 1: Extract Generic Core

Files: `crates/docs-gen/src/lib.rs`, `crates/docs-gen/src/host.rs:67-162`. Explicitly out of scope: `crates/sys/oxdock-process/src/expand.rs` (untouched, see Step 3).

- Create the generic core inside `docs-gen` (no separate crate).
  Move generic helpers into its `TEMPLATE` HostModule: `file_stem`,
  `has_key`, `map_set`, `to_json` with `value_to_json`,
  `expand_fragment` generalized. Keep the orchestration script in
  DSL: the `oxdock!` stages (`BUILD_MANIFEST`, `RENDER_TARGET`,
  duplicate target and stem guards) parameterized by config (`vars`
  mapping, `staging_dir`, `version_key`) instead of hardcoded names.
- Generalize `expand_fragment(raw, global, ctx, version)` to `expand_template(raw, vars: Map<String, Value>, env: Map<String, String>)`. No hardcoded `docs_global`, `docs_ctx`, `CRATE_VERSION`. Callers pass var map.
- `StreamingExpand` keeps its streaming tokenizer. No Markdown or
  JSON logic enters `sys/oxdock-process`. The placeholder
  call-expression hook (Step 3) dispatches to already registered host
  functions; the `MARKDOWN` module must be registered at render time
  for `{{ MARKDOWN::MAP_TO_MD_TABLE($var) }}` to resolve.
- Keep strict semantics: duplicate stem fails, duplicate target name fails, unknown placeholder fails, one trailing newline stripped at fragment stage, `\{{` escape preserved.
- New config schema (back compatible superset of `docs-gen.json` plus `target.json`):
  - `global_values`: string or list of paths. When a list is given, files merge in order with `merge_policy` below.
  - `merge_policy`: exactly `"fail_on_duplicate"` (default) or `"overwrite"`. `fail_on_duplicate` errors on any duplicate top level key across `global_values` files. `overwrite` lets later files win. Example:
    ```json
    {
      "global_values": ["path/to/base.json", "path/to/override.json"],
      "merge_policy": "overwrite"
    }
    ```
  - `scopes`: list of dirs globbed for `**/target.json` (keep).
  - `fragments`: already `group -> [glob]` (keep).
  - Add `vars`: map of logical to concrete names, e.g. `{"global": "docs_global", "ctx": "docs_ctx", "files": "files"}` with defaults preserving current names.
  - Add `staging_dir`: default `target/<engine>-docs`, replaces hardcoded `target/oxdock-docs`.
  - Add `version_key`: optional env key to inject (e.g. `CRATE_VERSION` or empty).
  - `generated`: change from 7 fixed keys to list of `{key, out, provider, args}` entries resolved via provider registry.
- Outcome: resume example works: `values.json` holds person data, fragments hold sections (`experience`, `education`, `skills`), master orders them, output is `.md` or `.html` or `.tex`. Same for any README.

## Step 2: Provider Trait for Generated Content and Values Sync

Files: `crates/docs-gen/src/host.rs:211-303`, `crates/docs-gen/src/oxdock/command_ref.rs`, `crates/docs-gen/src/rust/cargo.rs`, `crates/docs-gen/src/rust/mod.rs`.

- Define the provider surface as HostModules plus narrow traits
  backing the DSL (traits exist so Rust embedders can call without
  DSL, but the DSL path is primary):
  - `trait GeneratedProvider { fn key(&self) -> &str; fn render(&self, ctx: &RenderCtx) -> anyhow::Result<String>; }` exposed to DSL as `TEMPLATE::GENERATED(key)` dispatching the registry, so `REFRESH_GENERATED` stays a DSL `FOR` loop over config `generated` entries.
  - `trait ValuesSync { fn sync(&mut self, target_dir: &Path, member_or_target: &str) -> anyhow::Result<Option<serde_json::Value>>; }` (mutable receiver plus explicit target dir, since sync writes `values.json`; no hidden I/O behind `&self`), exposed as DSL-callable sync funcs so `SYNC_MEMBER` stays a DSL loop.
  - `struct RenderCtx { root: PathBuf, version: Option<String>, global: serde_json::Value }`
- Move OxDock specifics into `oxdock-docs-provider` (or keep in
  `docs-gen` until the split):
  - `workspace_members`, `workspace_version`, `cargo_package`, `package_values_json` (Cargo plus `toml_edit`, committed `name` wins rule).
  - `command_index`, `command_body`, `function_reference`, `plugin_function_reference`, `plugin_type_reference` plus `command_ref.rs` renderers and `plugin_docs` OnceLock with `oxdock-ssh-plugin` and `oxdock-net-plugin` links.
  - `MARKDOWN` HostModule lives in `crates/plugins/oxdock-markdown-plugin`
    (done): `MAP_TO_MD_TABLE($map)` over the pure `markdown` module.
    Usable as `IMPORT [MARKDOWN]` then `LET $md_table = MAP_TO_MD_TABLE($map)`.
- Core has `NoopValuesSync` (leaves `values.json` untouched) and empty provider registry for generic users.
- `REFRESH_GENERATED` in `lib.rs:49-71` stays DSL: a `FOR` loop over config `generated` list calling the registry dispatch func. No hardcoded 7 writes, no native Rust orchestration rewrite. Missing provider fails with known keys listed (same UX as `plugin_entry` today).
- `docs-gen` keeps its `oxdock-core`, `oxdock-parser`, `oxdock-fs`, and plugin deps. Depending on OxDock is expected; agnosticism is about generic inputs and outputs, not dependency purity.

## Step 3: Markdown Table Module invoked as placeholder function call (Issue 170)

Done for the table core. Files: pure table logic in
`crates/plugins/oxdock-markdown-plugin/src/markdown.rs`
(`markdown::{escape_table_cell, map_to_table}`, the single source);
thin `MARKDOWN` HostModule in the same crate exposing
`MAP_TO_MD_TABLE`; `docs-gen` `command_ref.rs` imports escaping from
the plugin (no local copy).

- Single source rule: pure `map_to_table(value)` plus
  `escape_table_cell` live in the markdown plugin with no engine
  calls. Every consumer piggybacks on them: the placeholder call
  `{{ MARKDOWN::MAP_TO_MD_TABLE($var) }}` during expansion, the
  statement form in DSL scripts, and `docs-gen` reference renderers.
  No copies.
- DSL and placeholder share one syntax (per user, no bracket formatter language):
  ```
  IMPORT [MARKDOWN]
  LET $md_table = MAP_TO_MD_TABLE($map)
  ```
  and inside any template or fragment:
  ```
  {{ MARKDOWN::MAP_TO_MD_TABLE($var) }}
  ```
  Anything interpolated can invoke a pure function. No `{{ [markdown]... }}` syntax ships. The `FormatterRegistry` plus `FormattedPlaceholder` bracket grammar below is deleted in favor of this.
- Boundary rule: `expand.rs` never contains Markdown, serde, or table code. It resolves the call target from the already registered module registry (`MARKDOWN` registered at render time exactly like `DOCS`), evaluates args from the current vars scope, calls the host fn, and stringifies the returned `Value`. Formatting lives in the markdown plugin; `expand.rs` only dispatches.
- Integrate https://github.com/jzombie/rust-oxdock/issues/170 as core table logic plus thin DSL wrapper callable from placeholders, not an OxDock-only statement. Issue 170 asks: when a placeholder points to a MAP in Markdown, render a table. Scope stays per placeholder, so Markdown inside Rust comments and other hosts keeps working.
- Grammar: extend placeholder content from key path only to expression with one call form. Before implementing, formalize in core (reusing `oxdock-parser` call parsing, not a parallel tokenizer):
  ```rust
  pub enum PlaceholderExpr {
      Var { key_path: String },
      Call { module: String, func: String, args: Vec<ArgExpr> },
  }
  pub enum ArgExpr {
      Var { key_path: String },
      Literal(Value),
  }
  ```
  Rules: placeholder body is either the existing `$var.path` / `env:KEY` / `KEY` forms or `MODULE::FUNC(arg, ...)` where args are `$var.path` refs or string/int/bool literals. Module and func names follow existing HostModule registration charset. Arity and types checked against the registered signature. Unknown module or func fails strict listing registered names. Escaped `\{{` never enters expression parsing. Call output is terminal text, not re expanded.
- Proposed syntax: `{{ MARKDOWN::MAP_TO_MD_TABLE($my_map) }}` invokes the registered function during expansion and splices the returned STRING. It calls the same `map_to_table` the DSL statement calls. No `[json-ld]` formatter is planned. JSON-LD stays a normal template file.
- Design points for implementer:
  - Call evaluation happens after arg resolution from the current expansion scope (`$my_map` plus literals). Only pure value returning funcs are callable from placeholders; funcs returning handles, pipes, or performing I/O fail at registration or call time with a clear message.
  - `MAP_TO_MD_TABLE` accepts the same args in both paths so DSL statements and placeholder calls stay consistent (e.g. optional headers literal).
  - `markdown` table logic owns escaping in the plugin
    (`markdown::{escape_table_cell, map_to_table}`, covering pipe
    handling and anchor rules). `docs-gen` (`command_ref.rs`) imports
    from the plugin, so docs-gen tables, DSL output, and placeholder
    output stay byte consistent from one source. Nested MAP or LIST
    values fall back to embedded JSON string.
  - Single pass expansion stays. Formatter output is terminal text, not re expanded, so generated Markdown containing `{{ }}` stays literal (same guarantee as `\{{` escape chain today).
  - Markdown inside non Markdown hosts (Rust comments, HTML, source files) works because only the targeted placeholder is transformed. Rest of file passes through untouched.
- JSON-LD note: resume example ships a `jsonld.tmpl` fragment with plain `{{ $person.name }}` style placeholders producing a single JSON-LD entry. It may be invoked from a template or a function call. No engine serialization beyond normal expansion plus the existing strict JSON value encoding.
- Tests: MAP to table golden test (simple MAP, nested value, empty MAP) run twice, once via `MAP_TO_MD_TABLE` DSL statement and once via `{{ MARKDOWN::MAP_TO_MD_TABLE($map) }}` placeholder, asserting byte identical output; unknown module or func inside `{{ }}` fails strict, placeholder call output with literal `{{ }}` is not re expanded, JSON-LD template fixture renders parseable JSON with `@context`.

## Non Goals

- No full source code scaffolder in v1. The placeholder function call path plus templated JSON-LD prove the path.
- No `[json-ld]` engine formatter and no bracket formatter language. Function calls inside `{{ }}` cover formatting.
- No new template control flow language. Providers plus one formatter cover generation.
- No native Rust rewrite of the pipeline. DSL owns sequencing and writes; Rust owns pure helpers only.
- No final rename choice. Research task only.
- No MCP server in this plan. Engine exposes a plain lib API that a future MCP host can call.
- No org facade or profile README work. Only a templated JSON-LD example is covered, no formatter output.
- Keep deterministic `AGENTS.md` and `docs.rs` zero warning doctests as existing invariants, not new work.
