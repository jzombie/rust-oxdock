# Plan: Migrate Slow DSL Tests to In-Process

## Problem

The `commands_harness` compiles a Rust sub-crate (`ast_commands`) **~48 times** (once per DSL command test case) via `cargo run --quiet`. Each invocation copies the sub-crate to a temp dir, patches `Cargo.toml`, and runs a full `cargo build`. Even with shared `CARGO_TARGET_DIR`, this is the slowest part of the test suite.

Meanwhile, `oxdock-core/tests/commands.rs` already has 36 in-process tests that parse and execute DSL scripts directly (no compilation) using `run_script()`. They run in **0.48s** in parallel.

## Overlap with Existing Plans

- **`playful-cactus.md` Phase 5** describes an "In-Process Test Harness" via `build.rs` code generation. This is more ambitious than needed — we don't need code generation, just more `#[test]` functions.
- **`gentle-wolf.md` P7** mentions "Migrate all buildtime_macros fixtures to build.rs flow" — this covers the `buildtime_macros/*` integration fixtures, not the `commands_harness` DSL cases.
- **This plan** covers the `commands_harness` specifically (48 DSL function test cases).

## Implementation Steps

### Step 1: Add missing in-process tests to `oxdock-core/tests/commands.rs`

Follow existing conventions:
- `GuardedPath::tempdir()` + `guard_root()` for isolation (each test gets its own tempdir)
- `run_script()` helper for simple cases
- `oxdock_core::parse_script()` + `run_steps_with_context_result_with_io()` for complex cases
- `indoc!` for multi-line scripts
- `write_text()`, `create_dirs()`, `read_trimmed()`, `exists()` helpers
- `#[cfg_attr(miri, ignore = "...")]` where needed

**All tests use virtualized contexts (`GuardedPath`, `ExecState` instance maps), never process-global state (`std::env::set_current_dir`, `std::env::set_var`).** Existing tests already run in parallel safely (verified: 36 tests in 0.48s).

**File:** `crates/oxdock-core/tests/commands.rs`

### Step 2: Add compile-time exhaustiveness check for StepKind coverage

Replace runtime source-file scraping with a **compile-time exhaustive match**. When a new `StepKind` variant is added, the compiler forces this function to fail until a test dispatches it:

```rust
/// Compile-time invariant: when a new StepKind variant is added,
/// this match must be updated — the compiler will error otherwise.
fn _assert_step_kind_exhaustiveness(kind: &StepKind) {
    match kind {
        StepKind::Workdir(_) => {},
        StepKind::Workspace(_) => {},
        StepKind::Env { .. } => {},
        StepKind::InheritEnv { .. } => {},
        StepKind::Run(_) => {},
        StepKind::Echo(_) => {},
        StepKind::RunBg(_) => {},
        StepKind::Copy { .. } => {},
        StepKind::CopyGit { .. } => {},
        StepKind::Symlink { .. } => {},
        StepKind::Mkdir(_) => {},
        StepKind::Ls(_) => {},
        StepKind::Cwd => {},
        StepKind::Read(_) => {},
        StepKind::Write { .. } => {},
        StepKind::Append { .. } => {},
        StepKind::Expand { .. } => {},
        StepKind::AssertFile { .. } => {},
        StepKind::AssertDir(_) => {},
        StepKind::AssertAbsent(_) => {},
        StepKind::AssertStdout(_) => {},
        StepKind::WithIo { .. } => {},
        StepKind::WithIoBlock { .. } => {},
        StepKind::HashSha256 { .. } => {},
        StepKind::Exit(_) => {},
        StepKind::For { .. } => {},
        StepKind::If { .. } => {},
        StepKind::Assign { .. } => {},
    }
}
```

This lives in `commands.rs` as a private function. It's called from one `#[test]` with a dummy variant to trigger the compiler's exhaustiveness check. No filesystem access, no runtime scraping, works under Miri and `cargo package`.

### Step 3: Feature-gate the slow harness, retain smoke test

Do NOT delete `commands_harness.rs` or `ast_commands/`. Instead:

1. Feature-gate `commands_harness.rs` behind `slow-integration`:
   ```rust
   #![cfg(feature = "slow-integration")]
   ```

2. Retain a **minimal smoke test** that validates the full sub-process compilation and execution lifecycle (at least 2 representative command invocations — one simple like `write`, one complex like `copy_git`). This ensures the binary entrypoint, CLI lowered dispatch, and process-level stdin/stdout piping remain covered.

3. The `coverage.toml` enforcement and `ast_commands/src/main.rs` coverage logic remain intact within the feature-gated harness.

### Step 4: Clean up harness deps (optional, later)

After confidence period, remove from `oxdock-logic-tests/Cargo.toml` any dependencies exclusively used by the harness that are not needed by the smoke test. Keep `libtest-mimic` and `oxdock-fixture` if the smoke test still uses them.
